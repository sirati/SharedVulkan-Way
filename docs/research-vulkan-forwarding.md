# Forwarding Vulkan across a VM boundary — design-grounding research

Research for `shared_vulkan`. Written 2026-08-11.

Companion documents in this directory: `hardware-constraints.md` (measured facts
about the target machine), `requirements-shared-memory.md` (the arena
requirement this report is written to answer), `api-scale.md`,
`research-sharedgl.md` (separate stream).

## Terminology

Adopted from `requirements-shared-memory.md` and used consistently below:

- **GPU side** — the process holding the real Vulkan driver and the physical
  GPU. On `testhost` this is *inside the Windows VM*.
- **App side** — the process running the application, which we serve with a
  fake Vulkan ICD. On `testhost` this is the *Linux host*.

Either side may be Linux or Windows; either may be the VM. Where a cited source
uses "guest"/"host" in the conventional virtio sense I keep the source's words
inside quotations and translate in the surrounding text.

## 0. The short answer

**Protocol: solved, twice over, and reusable.** Venus gives a complete
direction-neutral wire format (`VK_EXT_command_serialization`, 134 lines of
spec, MIT) generated by 3,126 lines of Python. gfxstream gives a
battle-tested one that has shipped to hundreds of millions of Android emulator
users, generated by 12,671 lines of Python into ~248,000 lines of C++
(Apache-2.0 output, MIT generators). Neither needs to be invented.

**The passthrough arena: the design exists and is in production.** gfxstream's
`kBlobMemGuest` + `kBlobFlagCreateGuestHandle` path is precisely the
requirement in `requirements-shared-memory.md` — the app side allocates the
pages, the GPU side imports them with **`VK_EXT_external_memory_host`**, and
`vkMapMemory` returns a real pointer into shared pages with no copy anywhere.
It is the *less*-travelled of gfxstream's two paths but it is real code.

**Driver signing turned out not to be the blocker.** A Microsoft-signed ivshmem
driver for Windows exists — the one bundled with the Looking Glass B7 installer,
whose catalogue chains to `CN=Microsoft Windows Hardware Compatibility
Publisher`, i.e. it loads under Secure Boot with no test-signing. (The driver
the older instructions point at, from `virtio-win-0.1-161`, is cross-signed by
Red Hat *after* Microsoft's 2015 cutoff and does **not** load under Secure Boot;
that is the source of the widespread belief that ivshmem needs test-signing.)
Current virtio-win ships no ivshmem driver at all, but it does ship signed
`viosock`, `vioser` and `netkvm` (and the mounted guest-tools ISO on this
machine is 0.1.285, which includes `viosock`). So the shared-memory route is
open — but it turns out we can very likely do better: ordinary guest RAM, no
device, no driver at all, via Windows **AWE** (`AllocateUserPhysicalPages`),
which returns real guest-physical frame numbers a user-mode process can hand to
the host. That is now the primary plan (§2.2), with an attestation-signed
200-line pinning driver as the fallback and ivshmem only as a last resort.

**The real blocker, if there is one, is whether the GPU-side driver will import
our arena.** `VK_EXT_external_memory_host` is the mechanism, gfxstream uses it
in production for exactly this purpose, and it either works on Intel's Windows
driver or the zero-copy requirement is unreachable in this form. That is one
afternoon's measurement and it should precede all other work.

**Scope reality check.** Zink is achievable. DXVK ≤ 2.6 is achievable. DXVK
≥ 2.7 and vkd3d-proton require `bufferDeviceAddress` with shaders that
dereference raw 64-bit VAs, which a forwarder cannot intercept. The "single
waist of the hourglass" does not hold for D3D12. See §5.

### 1.2 Venus

Three parts, all permissive — licence headers verified directly in the files:
`vn_protocol.py` and Mesa's `vn_ring.h`/`vn_renderer.h`/`vn_device_memory.h`
carry `SPDX-License-Identifier: MIT`; `VK_MESA_venus_protocol.xml` carries
`Apache-2.0 OR MIT`.

- Protocol + generator: <https://gitlab.freedesktop.org/virgl/venus-protocol>
- App-side driver: <https://gitlab.freedesktop.org/mesa/mesa/-/tree/main/src/virtio/vulkan>
- GPU-side renderer: <https://gitlab.freedesktop.org/virgl/virglrenderer/-/tree/main/src/venus>
- <https://docs.mesa3d.org/drivers/venus.html>

**Generation.** Three XML files and two Python modules:

```
xmls/vk.xml                             (Khronos, verbatim)
xmls/VK_EXT_command_serialization.xml   (588 lines, 456 <enum> entries)
xmls/VK_MESA_venus_protocol.xml         (315 lines)
vkxml.py                                (1150 lines — registry parser)
vn_protocol.py                          (1976 lines — generator)
```

**3,126 lines of Python generating the entire marshalling layer for both
sides.** Output is `vn_protocol_driver_*.h` (app side) and
`vn_protocol_renderer_*.h` (GPU side), each with `vn_sizeof_*`, `vn_encode_*`,
`vn_decode_*` and dispatch per command. 456 serialised commands against 709
non-alias commands in the full registry — Venus deliberately skips the third
it cannot serialise.

**Wire format** (`docs/VK_EXT_command_serialization.txt`, 134 lines — short
enough to reimplement, precise enough to be worth following):

| DW | Command stream | | DW | Reply stream |
|---|---|---|---|---|
| 0 | `VkCommandTypeEXT` | | 0 | `VkCommandTypeEXT` |
| 1 | `VkCommandFlagsEXT` | | 1-N | return value + out params |
| 2-N | parameters | | | |

- Command length is **implicit** in the type; unknown commands cannot be
  skipped. Both ends must agree on the protocol version exactly.
- A reply is generated only when `VK_COMMAND_GENERATE_REPLY_BIT_EXT` is set, so
  most calls are fire-and-forget.
- Integers little-endian padded to 32 bits; floats reinterpret-cast; enums as
  `int32_t`; `size_t` as `uint64_t`.
- Handles (dispatchable or not) serialise as a `uint64_t` **object id**;
  `VK_NULL_HANDLE` is 0.
- Non-`void` pointers: `uint64_t` count then the values; padding after all
  values, not each.
- `pNext` `void*` is "serialized as a pointer to a struct whose type is
  determined by `VkStructureType`". A sized `void*` is a blob (`uint8_t*`);
  `char*` is a blob including the NUL.
- Unions: `uint32_t` member index, then the member.
- For output pointers the pointee is assumed uninitialised **except** `sType`,
  `pNext`, handles and `uint32_t` size params — handling the count-then-fill
  idiom.

And the exclusion list, verbatim and load-bearing:

> When a command parameter is not of a type with a serialization specified, it
> is not serializable. This includes, but is not limited to,
>
>  - function pointers
>  - **pointers to mapped memory object regions**
>  - WSI handles
>  - external handles

Mapped memory is *explicitly out of scope of the protocol*. Venus does not
serialise it and cannot; it requires the pages to be genuinely shared. This is
the same conclusion `requirements-shared-memory.md` reaches from the other
direction.

Two honest caveats the spec makes about itself: "There may also be bugs (grep
WA) in the codegen", and "It is impossible to distinguish `NULL` and a
non-`NULL` pointer with zero value after serialization." It is a working
document, not a ratified standard.

**The ring.** Defined in the protocol XML as `VkRingCreateInfoMESA`
(`resourceId, offset, size, idleTimeout, headOffset, tailOffset, statusOffset,
bufferOffset, bufferSize, extraOffset, extraSize`) and mirrored exactly by
`struct vn_ring_layout` in Mesa. From `vn_ring.h`:

> A ring is a single-producer and single-consumer circular buffer. […] An
> externally-defined mechanism is required for ring setup and notifications in
> both directions. Notifications for new data from the producer are needed only
> when the consumer is not actively polling, which is indicated by the ring
> status.

Status bits: `VK_RING_STATUS_IDLE_BIT_MESA`, `_FATAL_BIT_`, `_ALIVE_BIT_`. The
consumer (`virglrenderer/src/venus/vkr_ring.c`) runs a thread per ring that
**spins while work arrives** and only sleeps after `idleTimeout` with an empty
ring, at which point it sets the IDLE bit and blocks on a condvar until
`vkNotifyRingMESA`. Ordering is explicit C11 atomics:

```c
/* the renderer is expected to load the head with memory_order_acquire, ... */
atomic_store_explicit(ring->control.head, ring_head, memory_order_release);
/* the driver is expected to store the tail with memory_order_release, ... */
return atomic_load_explicit(ring->control.tail, memory_order_acquire);
```

This hybrid spin-then-sleep design maps 1:1 onto `ivshmem-doorbell` and is
directly reusable. gfxstream's ASG ring (§1.3) reaches the same design
independently, which is strong evidence it is the right one.

`VK_MESA_venus_protocol.xml` also defines 18 protocol-level commands — a good
checklist of what a forwarder needs *beyond* Vulkan:

```
vkCreateRingMESA  vkDestroyRingMESA  vkNotifyRingMESA  vkWriteRingExtraMESA
vkWaitRingSeqnoMESA  vkExecuteCommandStreamsMESA
vkSetReplyCommandStreamMESA  vkSeekReplyCommandStreamMESA
vkSubmitVirtqueueSeqnoMESA  vkWaitVirtqueueSeqnoMESA
vkGetMemoryResourcePropertiesMESA  vkImportSemaphoreResourceMESA
vkWaitSemaphoreResourceMESA  vkResetFenceResourceMESA
vkCopyImageToMemoryMESA  vkCopyMemoryToImageMESA
vkWriteResourceDescriptorMESA  vkWriteSamplerDescriptorMESA
```

**Transport abstraction and its limit.** `vn_renderer.h` defines a clean vtable
(`ops`/`shmem_ops`/`bo_ops`/`sync_ops`) with exactly two backends:
`vn_renderer_virtgpu.c` (1262 lines, DRM ioctls — app-side-in-guest only) and
`vn_renderer_vtest.c` (1080 lines, **a plain `AF_UNIX` socket** to
`virgl_test_server`). The vtest backend proves the protocol runs with no VM and
no kernel driver. But its memory sharing is file-descriptor passing:

```c
/* vtest_bo_map() */
void *ptr = mmap(placed_addr, bo->base.mmap_size, PROT_READ | PROT_WRITE,
                 MAP_SHARED | (placed_addr ? MAP_FIXED : 0), bo->res_fd, 0);
```

with `res_fd` arriving over `SCM_RIGHTS`. Same-kernel only. And
`vtest_bo_flush`/`vtest_bo_invalidate` are both literally `/* nop */`, because
the mapping is genuinely the same physical memory.

**Direction verdict for Venus.** The *protocol* is direction-neutral. The
*implementation* is not, and — per the gfxstream investigation — Venus is
actually **more** committed to the conventional direction than gfxstream is.
`vn_renderer_virtgpu.c` says so explicitly:

```c
/* VIRTGPU_BLOB_MEM_GUEST allocates from the guest system memory.  They are
 * logically contiguous in the guest but are sglists (iovecs) in the host.
 * That makes them slower to process in the host.  With host process
 * isolation, it also becomes impossible for the host to access sglists
 * directly. ... it seems the easiest way is to reuse VIRTGPU_BLOB_MEM_HOST3D. */
gpu->shmem_blob_mem = VIRTGPU_BLOB_MEM_HOST3D;
```

Venus deliberately abandoned app-side-allocated shared memory. gfxstream kept
it. **For our inverted topology gfxstream is the better starting point**, and
Venus's contribution is the wire format and the ring.

Mesa's own documentation is candid that even in the supported direction the
memory model is on thin ice:

> The renderer makes assumptions about `VkDeviceMemory` that has
> `VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT` that are illegal and rely on current
> behaviors of host drivers.

**Venus on Windows — an existence proof.** virglrenderer's venus renderer
already has a macOS backend in tree (`src/venus/vkr_metal_helpers.m`), and
**WINQ-EMU** (<https://github.com/cmspam/winq-emu>) states it "ported
virglrenderer's Venus Vulkan forwarding to Windows" including "Windows dma-buf
shims". Its *direction* is conventional, so it is not our topology, but it
establishes that a Venus-style GPU-side renderer runs on Windows. Licences
stated: QEMU GPL-2.0, virglrenderer MIT, launcher MIT. I did not verify the
diff or whether the patches are upstreamed.

### 1.3 gfxstream — the most directly relevant prior art

Repos (both live and current): canonical
<https://android.googlesource.com/platform/hardware/google/gfxstream/>, mirror
<https://github.com/google/gfxstream>. Predecessor: `vulkan-cereal`.

**Important structural fact: the two halves are now in different projects.**
The app-side Vulkan encoder has moved out of the gfxstream repo into Mesa as an
ordinary Vulkan driver — <https://gitlab.freedesktop.org/mesa/mesa/-/tree/main/src/gfxstream/>,
shipping an ICD manifest `gfxstream_vk_devenv_icd.x86_64.json`. The GPU-side
decoder remains a standalone C++ library in the gfxstream repo.

**Licences:** gfxstream `LICENSE` is **Apache-2.0**; generated host and app-side
files carry Apache-2.0 headers; the *generator scripts* in Mesa
(`cerealgenerator.py`, `cereal/*.py`) are **MIT**. All permissive. Apache-2.0
is GPLv3-compatible but not GPLv2-compatible, if that ever matters.

**Scale — the single best effort estimate available.** Real `wc -l` on a
checkout:

| | lines |
|---|---:|
| Python generators (`cereal/` + `cerealgenerator.py`) | **12,671** |
| Generated app-side C++ (`VkEncoder.cpp` alone: 27,967) | **117,298** |
| Generated GPU-side C++ (`vk_decoder.cpp` alone: 23,225) | **~130,900** |
| **Generated total** | **~248,000** |
| Hand-written app-side glue (`ResourceTracker.cpp` 8,091 + ~4,500) | ~12,600 |
| Hand-written GPU-side glue (`vk_decoder_global_state.cpp` 12,786 + `vk_common_operations.cpp` 5,251) | ~18,000 |

The generated 248k is nearly free once the generator exists. **The ~30k of
hand-written semantic glue is the real cost of the project.**

**The pass taxonomy** — this is the most reusable artefact in the whole
investigation, because each pass is a separate full walk over every Vulkan
struct and each exists for a reason we would otherwise discover painfully:

1. **`counting`** (app side) — computes the exact serialised size so a
   contiguous span can be reserved in the ring *before* writing. Emits literal
   `*countPtr += <sizeExpr>;`.
2. **`reservedmarshaling`** (both) — the hot path. Writes into a caller-supplied
   `uint8_t** ptr` that it bumps: **zero-copy straight into the ring**, no
   intermediate buffer. Requires `counting` to have run. The mirror
   `reservedunmarshal_*` reads *in place out of the ring* and fixes pointers to
   point into the ring itself. The (count, reserve, marshal) triple is the
   entire performance story.
3. **`marshaling`** (both) — the older safe path through a `VulkanStream` with
   `write()`/`read()` virtuals, kept in parallel for cold paths and snapshots.
4. **`deepcopy`** (both) — copies a struct graph into a `BumpPool`, flattening
   `const T*` members and pNext chains. Needed because the GPU side must retain
   arguments past the lifetime of the ring slot, and because unboxing mutates
   handles in place and must not scribble on the app side's ring.
5. **`handlemap`** — generic "walk the struct, apply a mapping to every handle
   field".
6. **`transform`** (`transform_tohost_*` / `transform_fromhost_*`) — *semantic*,
   not syntactic. Where app-side-visible values become GPU-side values.
   `deviceMemoryTransform()` rewrites the `(handle, offset, size, typeIndex,
   typeBits)` tuple everywhere it appears, because one app-side `VkDeviceMemory`
   is a *suballocation* of a larger GPU-side block. **We will need this pass; it
   is neither optional nor mechanical.**
7. **`dispatch`** (GPU side) — builds dispatch tables. In Rust, `ash` gives this
   for free.
8. **`extensionstructs`** — pNext tables, see below.
9. **`decoder`** (GPU side) — the giant opcode switch, plus the seqno protocol.
10. **`subdecode`** (GPU side, 4,588 lines) — a *second*, restricted decoder for
    a blob of pre-recorded `vkCmd*` calls delivered in one packet. The
    command-buffer batching mechanism.
11. **`decodersnapshot`** (7,063 lines) — VM snapshot/restore. **Skip entirely.**
12. `functable`, `api_log_decoder`, `testing` — proc-address tables, a trace
    decoder, generated round-trip tests.

**pNext encoding** (from `extensionstructs.py`, 125 lines). Three design
decisions worth copying deliberately: each link is **length-prefixed with a
0 terminator**, so a reader can skip without the type table; **unknown links
are silently dropped and the walk continues down `pNext`** on the app side but
are a **fatal abort** on the GPU side (asymmetric on purpose — clients lenient,
servers strict); and a `rootType` is threaded through everything because the
same struct type means different things depending on which root it hangs off.

**Boxed handles — the security and lifetime backbone.** Two levels:

*Level 1, app-side wrapper.* The app side never hands the real GPU-side handle
to the application. It allocates `struct goldfish_VkDevice { uint64_t
underlying; VkEncoder* lastUsedEncoder; uint32_t sequenceNumber; ... }` and
returns a pointer to *that* as the `VkDevice`, with `loaderMagic =
ICD_LOADER_MAGIC` set so it is a valid loader-dispatchable object. This lets
per-object state hang off *any* handle including non-dispatchable ones, which
are otherwise bare u64s with nowhere to attach metadata.

*Level 2, GPU-side boxing.* `underlying` is not the driver's handle either; it
is a u64 index into a `BoxedHandleManager`, where each entry holds
`{underlying, dispatch, ordMaintInfo, readStream}` plus a type tag. Five
reasons, all of which apply to us:

1. **Security** — a malicious app side can only send a u64 index. A bad index
   fails a lookup; it never becomes a wild pointer in the GPU-side driver.
2. **Handle stability** across snapshot/restore.
3. **Dispatch attachment** — the decoder resolves the right ICD entrypoint from
   the handle.
4. **Ordering** — per-object `{seqno, lock, condvar, refcount}` serialises
   concurrent access from multiple decoder threads.
5. **Deferred destruction** — `removeDelayed(h, device, callback)` keeps the
   mapping alive until the GPU is genuinely done, invisibly to the app side.

In Rust this is a `SlotMap<Key, HandleInfo>` and most of it comes free. **This
directly answers requirement 5 (lifetime and safety) and should be adopted
wholesale.**

**Escape hatches, as a warning.** `marshalingdefs.py` holds
`CUSTOM_MARSHAL_TYPES` — types whose marshal bodies are hand-written C++
because vk.xml cannot describe them (currently
`VkAccelerationStructureInstanceKHR`, whose bitfields are undescribable) — and
`STRUCT_ENV_STR`, which is **a small Lisp**:

```
"hasRasterization": "(or (if (eq 0 pRasterizationState) 0
                     (not (getfield pRasterizationState rasterizerDiscardEnable))) ...)"
```

used to decide whether `pTessellationState` is actually present in
`VkGraphicsPipelineCreateInfo`. vk.xml's `optional`/`len` attributes are *not*
sufficient to decide whether a pointer must be followed. **Every Vulkan
serialiser eventually needs an expression language here. Budget for it.**

**Custom protocol commands.** `codegen/xml/vk_gfxstream.xml` defines 27
`vk*GOOGLE` entrypoints — `vkQueueSubmitAsyncGOOGLE`,
`vkQueueFlushCommandsGOOGLE`, `vkBeginCommandBufferAsyncGOOGLE`,
`vkCreateImageWithRequirementsGOOGLE`, `vkMapMemoryIntoAddressSpaceGOOGLE`,
`vkGetBlobGOOGLE`, `vkGetMemoryHostAddressInfoGOOGLE`, `vkGetSemaphoreGOOGLE`,
`vkCollectDescriptorPoolIdsGOOGLE` and others. **The protocol is not "Vulkan
verbatim" — it is Vulkan plus ~27 invented calls whose entire purpose is to
eliminate round trips.** That list is a ready-made checklist.

**The ASG ring**, for comparison with Venus's:

```c
struct ring_buffer {               /* "can be shared between host and guest as-is" */
    uint32_t host_version, guest_version;
    uint32_t write_pos;   uint32_t unused0[13];   /* cache-line separated */
    uint32_t read_pos, read_live_count, read_yield_count, read_sleep_us_count;
    uint32_t unused1[12];
    uint8_t  buf[2048];
    uint32_t state;                /* NEED_NOTIFY | CAN_CONSUME | EXIT | ERROR | RENDERING */
    uint32_t config[32];
};
```

Small packets go through the 2 KiB ring; large payloads live in a separate
shared buffer with only a descriptor in the ring. While the consumer is hot the
producer writes and never traps; only when the consumer has parked
(`NEED_NOTIFY`) does the producer pay for a notification. The adaptive backoff
counters live *in shared memory* so the producer can see them. Independent
convergence with Venus on spin-then-sleep.

**Sequence numbers.** Separate from the ring, for cross-thread ordering, and
the counter itself is a **shared-memory word** rather than a message field:

```cpp
/* app side */ uint32_t seqno = ResourceTracker::nextSeqno();  /* atomic add on a SHARED word */
/* GPU side */ while ((seqno - seqnoPtr->load(std::memory_order_seq_cst) != 1)) { /* spin/yield */ }
               seqnoPtr->fetch_add(1, std::memory_order_seq_cst);  /* after EVERY command */
```

So many independent rings still get a global total order with no cross-thread
messaging.

**Command-buffer batching.** `vkCmd*` calls are not sent individually. A
`CommandBufferStagingStream` — itself backed by *Vulkan device memory*, with an
8-byte `kSyncDataReadPending`/`kSyncDataReadComplete` handshake word so the app
side does not free a buffer the GPU side is still reading — accumulates encoded
packets locally, and one `vkQueueFlushCommandsGOOGLE` carries the whole blob at
submit time. `vkQueueFlushCommandsFromAuxMemoryGOOGLE` handles the case where
the blob already sits in the shared buffer: **zero copies from record to
execute.**

### 1.4 rutabaga_gfx, and `kumquat`

**It has moved.** crosvm HEAD no longer contains `rutabaga_gfx/`; it depends on
the crates.io package. Source of truth is now
<https://github.com/magma-gpu/rutabaga_gfx>, currently 0.1.85.
**Licence BSD-3-Clause**, published on crates.io as `rutabaga_gfx` and
`rutabaga_gfx_ffi`, `rust-version = 1.81.0`, edition 2021, only **7,330 lines
of Rust**. Maximally convenient for a Rust project.

It contains **no renderer**. It is a multiplexer: virtio-GPU commands in,
dispatched by *context type* to a component. Capsets:

| id | name | component | meaning |
|---:|---|---|---|
| 1/2 | `virgl`, `virgl2` | virglrenderer | OpenGL command stream |
| 3 | `gfxstream-vulkan` | gfxstream | the gfxstream Vulkan protocol |
| 4 | `venus` | virglrenderer | Mesa venus ↔ `vkr` |
| 5 | `cross-domain` | CrossDomain | Wayland/DRM/camera/PipeWire/X11/D-Bus socket proxying |
| 6 | `drm` | virglrenderer | **native contexts** — serialise the vendor's *kernel ioctl stream*, run the real vendor UMD app-side |
| 7 | `magma` | Magma | OS-agnostic GPU syscall interface |
| 8/9 | `gfxstream-gles`, `gfxstream-composer` | gfxstream | |

"Native contexts" (capset 6) is the conceptual alternative to API forwarding:
much less code and better performance, but hardware-family-specific, and it
requires the app side to run the same vendor UMD — which is exactly what a
GPU-less Linux machine cannot usefully do when the kernel driver is on the
other side. **Not applicable to us.**

**QEMU's `virtio-gpu-rutabaga-pci`** (`hw/display/virtio-gpu-rutabaga.c`,
v10.2.0) exposes only these properties:

```c
DEFINE_PROP_BIT64("gfxstream-vulkan",     ..., RUTABAGA_CAPSET_GFXSTREAM_VULKAN,  false),
DEFINE_PROP_BIT64("cross-domain",         ..., RUTABAGA_CAPSET_CROSS_DOMAIN,      false),
DEFINE_PROP_BIT64("x-gfxstream-gles",     ..., RUTABAGA_CAPSET_GFXSTREAM_GLES,    false),
DEFINE_PROP_BIT64("x-gfxstream-composer", ..., RUTABAGA_CAPSET_GFXSTREAM_COMPOSER,false),
```

**No `venus`, no `virgl`, no `drm`.** So on QEMU 10.2.2,
`virtio-gpu-rutabaga-pci` *is* "gfxstream decoder, in-process, in the VMM" —
and its direction is the conventional one (app side in the guest). It is not
directly usable for us, but its presence means the gfxstream stack is already
packaged on this machine's QEMU.

**`kumquat` is the finding that matters.** `rutabaga_gfx/kumquat/server/` is a
**710-line standalone rutabaga server that speaks over a UNIX socket with no
virtual machine at all**, and Mesa carries a matching client backend at
`src/gfxstream/guest/platform/kumquat/`. Usage from the README:

```sh
cd rutabaga_gfx/kumquat/server/ && cargo build --features=gfxstream && ./target/debug/kumquat
# client:
meson setup guest-build -Dvulkan-drivers="gfxstream" -Dvirtgpu_kumquat=true ...
```

## 2. The passthrough arena

This section answers the five questions in `requirements-shared-memory.md`.

### 2.0 Why a copying design is not merely slow but non-conformant

From the Vulkan specification source
(`Vulkan-Docs/chapters/memory.adoc`, lines 675-681):

```
There must: be at least one memory type with both the
ename:VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT and
ename:VK_MEMORY_PROPERTY_HOST_COHERENT_BIT bits set in its
pname:propertyFlags.
There must: be at least one memory type with the
ename:VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT bit set in its propertyFlags.
```

So the tempting escape — advertise only non-coherent `HOST_VISIBLE` memory so
that applications are *forced* to call `vkFlushMappedMemoryRanges` where we can
intercept — **is not legal as the only option**. A conformant implementation
must expose at least one coherent host-visible type, and an application may
legally map it once and write forever with no further API call. There is no
hook.

This is why every serious forwarder maps real pages, and it is why the arena
requirement is the right requirement rather than a performance nicety.

### 2.1 Q1 — How does the GPU side turn arena pages into `VkDeviceMemory`?

**`VK_EXT_external_memory_host`, and this is not speculation — it is what
gfxstream does in production.**

The extension is confirmed present in local `vk.xml` (number 179,
`supported="vulkan,vulkansc"`, ratified, `depends="VK_KHR_external_memory,VK_VERSION_1_1"`),
defining `VK_EXTERNAL_MEMORY_HANDLE_TYPE_HOST_ALLOCATION_BIT_EXT`,
`VK_EXTERNAL_MEMORY_HANDLE_TYPE_HOST_MAPPED_FOREIGN_MEMORY_BIT_EXT`,
`VkImportMemoryHostPointerInfoEXT`, `VkMemoryHostPointerPropertiesEXT`,
`VkPhysicalDeviceExternalMemoryHostPropertiesEXT` and
`vkGetMemoryHostPointerPropertiesEXT`.

gfxstream's app side, when `kParamCreateGuestHandle` is available, takes the
**`kBlobMemGuest | kBlobFlagCreateGuestHandle`** path
(`ResourceTracker::allocateCoherentMemory`): the app side allocates the pages
and exports them, and the GPU side imports them. The GPU-side import code
(`vk_decoder_global_state.cpp`) builds a `VkImportMemoryHostPointerInfoEXT` and
— note this defensive detail, which we must copy — **rewrites the memory type
index if the driver rejects the app side's choice**:

```c
if (((1u << localAllocInfo.memoryTypeIndex) & memoryHostPointerProperties.memoryTypeBits) == 0) {
    for (uint32_t i = 0; i <= 31; ++i) { if (...) { localAllocInfo.memoryTypeIndex = i; break; } }
}
vk_append_struct(&structChainIter, &importHostInfo);
```

So `vkGetMemoryHostPointerPropertiesEXT` returning a `memoryTypeBits` mask that
excludes your preferred type is a *normal, expected* condition to handle, not a
failure.

**Suballocation is mandatory, and brings a required protocol pass.** In
gfxstream one app-side `VkDeviceMemory` is *not* one GPU-side allocation.
`CoherentMemory` wraps a 16 MiB region (`kDefaultHostMemBlockSize`) with Mesa's
`u_mm` heap allocator and suballocates 4 KiB-aligned chunks, rounding small
allocations up to 1 MiB and bundling them. Every `(memory, offset)` pair
crossing the wire therefore gets rewritten by `deviceMemoryTransform()` in
`transform.py`. **Our arena allocator will need the same, and the offset-rewrite
pass is not optional.**

**Two driver facts I verified directly from Mesa source**, both encouraging:

```c
/* src/intel/vulkan/anv_physical_device.c */
/* VK_EXT_external_memory_host */
{
   props->minImportedHostPointerAlignment = page_size;
}
```

```c
/* src/gallium/frontends/lavapipe/lvp_device.c */
.EXT_external_memory_host              = true,
...
/* VK_EXT_external_memory_host */
.minImportedHostPointerAlignment = 4096,
```

#### Driver support matrix

| Driver / platform | `HOST_ALLOCATION` | `minImportedHostPointerAlignment` | Notes |
|---|---|---|---|
| **Intel Windows (Raptor Lake-P)** | **Yes** | **4096** | Inferred from sibling PCI IDs — see below |
| Intel ANV (Linux) | Yes, gated `has_userptr_uapi` | `page_size` → 4096 | true on both i915 and Xe |
| RADV (AMD Linux) | Yes, gated `has_userptr` | 4096 | **but see the ANONONLY trap below** |
| AMD Windows (Adrenalin) | Yes | 4096 | |
| NVIDIA proprietary (both OSes) | Yes | 4096 | since ~440.66.17 |
| **NVK** (Mesa's open NVIDIA) | **No** | — | not exposed at all |
| Turnip | **No** | — | |

| MoltenVK / SwiftShader | Yes | 16384 / 16 | the only modern outliers on alignment |

The Mesa drivers implementing the extension at all are: hasvk, anv, radv, dzn,
kosmickrisp, lavapipe.

**On the Raptor Lake-P claim.** `vulkan.gpuinfo.org` *is* scriptable — the
working endpoint is the internal DataTables one,
`https://vulkan.gpuinfo.org/api/internal/devices.php`, which 500s unless sent
the complete DataTables parameter set (`draw`, `start`, `length`, every
`columns[i][...]`, `order[0][...]`, `search[value]`), with filters under
`filter[...]`. That is why my earlier attempts returned nothing. 87 of 99
distinct Intel Windows devices expose the extension; the 12 that do not are all
pre-2018 non-DCH parts, first appearance being driver 100.8439 (2020-11-28).
**No report with deviceID exactly `0xA7A8` exists**, so this is inference, not
observation — but `0xA7A8` sits in the same RPL-P macro block as `0xA7A0` and
`0xA7AA` in the kernel's `pciids.h`, i.e. identical silicon and driver path, and
all three siblings report the extension with alignment 4096
([id=44652](https://vulkan.gpuinfo.org/displayreport.php?id=44652),
[id=31774](https://vulkan.gpuinfo.org/displayreport.php?id=31774),
[id=48370](https://vulkan.gpuinfo.org/displayreport.php?id=48370)).

**On alignment: query it, but 4096 is safe to design around.** Windows-wide,
945 devices report 4096 against 29 at 65536; Linux, 909 against 3. All 26 Intel
devices reporting 65536 are on driver ≤ 100.8190 — Intel flipped to 4096 in May
2020, long before Raptor Lake. No NVIDIA or AMD device anywhere reports 65536.
Note the size constraint as well as the address:
`VUID-VkMemoryAllocateInfo-allocationSize-01745` requires `allocationSize` to be
an integer multiple of the same alignment.

#### ⚠️ RADV rejects *all shared* mappings, not just BARs

This is the most consequential finding for the OS-agnostic goal, and it is easy
to miss. libdrm's `amdgpu_create_bo_from_user_mem` passes
`AMDGPU_GEM_USERPTR_ANONONLY` **unconditionally**, and the kernel enforces
(`amdgpu_ttm.c`):

```c
	if (unlikely((gtt->userflags & AMDGPU_GEM_USERPTR_ANONONLY) &&
		vma->vm_file)) {
		r = -EPERM;
```

That rejects any VMA with a backing file — and on Linux
`MAP_SHARED|MAP_ANONYMOUS` *has* one, because `mm/vma.c` calls
`shmem_zero_setup()` for fileless shared mappings. **So on RADV,
`VK_EXT_external_memory_host` accepts only `MAP_PRIVATE|MAP_ANONYMOUS` memory —
ordinary heap. It cannot import a memfd, `/dev/shm`, `MAP_SHARED|MAP_ANONYMOUS`,
or a PCI BAR.** A shared arena is shared by construction, so this mechanism is
unusable on AMD/Linux regardless of the BAR question, and it surfaces
synchronously as `VK_ERROR_INVALID_EXTERNAL_HANDLE` from `vkAllocateMemory`.

ANV/i915 has no such restriction — it rejects only iomappings — so memfd works
there. **The design consequence is that the arena import path must be
pluggable**: host-pointer import where it works (Intel, NVIDIA), dma-buf import
on AMD/Linux. Since the brief requires either side to be either OS, this is not
an optional refinement.

#### lavapipe is a great harness and a dangerous oracle

lavapipe's properties query does no validation whatsoever —
`pMemoryHostPointerProperties->memoryTypeBits = 1; return VK_SUCCESS;` — and the
allocation simply adopts the pointer
(`mem->mem_alloc.cpu_addr = mem->vk.host_ptr`). It is a CPU rasteriser: no DMA,
no pinning.

So it will cheerfully "import" a pointer that every real driver rejects.
**Use lavapipe to develop the API plumbing; never treat a lavapipe pass as
evidence that the memory mechanism works.** With that caveat, it remains the
right development target: the entire GPU side can be built and tested on an
ordinary Linux box with no GPU and no VM, which — with Mesa's
`zink-venus-lavapipe` CI job (§5.1) — gives a complete loop that never risks the
family laptop's display. That is the mitigation for R18 and the reason §7.3 is
ordered as it is.

#### What the driver gives back

Worth knowing before designing the memory-type table of §2.4:

- **RADV returns exactly one memory type** — the first GTT domain type without
  `RADEON_FLAG_GTT_WC`, whose flags are `HOST_VISIBLE | HOST_COHERENT |
  HOST_CACHED`. So imported pointers land in cached coherent GTT, or
  `memoryTypeBits == 0` if no such type exists.
- **ANV returns the default buffer memory types** on Xe2+ (all non-protected,
  non-compressed) or all types on older gens — i.e. it lets us choose.
- The spec says `memoryTypeBits` "**should** only include bits that identify
  memory types which are host visible", and that implementations "**should not**
  support importing host pointers for memory types which are not host-visible"
  on general-purpose operating systems. So on desktop we may assume host-visible.
- **ANV's `vkMapMemory` returns the pointer we imported** (`*ppData =
  mem->vk.host_ptr + offset`). Convenient, but the spec explicitly does not
  require it (Issue 4: "Implementations are allowed to return the same address
  but it is not required"), so do not depend on it.
- **A caveat that matters for §2.3:** imported memory "is not considered to be
  host mapped device memory unless it is also explicitly host mapped using
  `vkMapMemory`", so flushing or invalidating host caches with respect to
  accesses "**through the original host pointer** … is the responsibility of the
  application and must be performed with appropriate synchronization primitives
  provided by the platform which are outside the scope of Vulkan." In other
  words `vkFlushMappedMemoryRanges` does not necessarily cover our own arena
  pointer. On x86 with a WB mapping this is a non-issue; it would matter on a
  weakly-ordered platform.

**The remaining question is the Windows side**, and it is the one to settle
first. What I can state now:

- gfxstream relies on this path in shipping Android emulator configurations,
  which is strong evidence that mainstream desktop drivers implement it.
- Search results indicate Intel's *Windows* driver has listed
  `VK_EXT_external_memory_host` since roughly 31.0.101.3790
  (<https://www.geeks3d.com/20221031/intel-graphics-driver-31-0-101-3790-released-vulkan-1-3-228/>).
  **I could not verify this from a primary source.** `vulkan.gpuinfo.org`'s
  coverage pages are JavaScript-driven and its `listdevicescoverage.php` and
  `/api/v3/` endpoints returned nothing usable to `curl`.
- **This must be measured on the actual machine, and it is a five-minute
  check.** Run `vulkaninfo` in the Windows guest; grep for
  `VK_EXT_external_memory_host`; read `minImportedHostPointerAlignment`; then
  write a ten-line program that calls `vkGetMemoryHostPointerPropertiesEXT` on
  (a) an ordinary `VirtualAlloc` pointer and (b) a pointer into whatever the
  arena will actually be, and check `memoryTypeBits != 0` in both cases. Do
  this before writing protocol code.

**Fallbacks if it is absent**, in rough order of preference:

1. **dma-buf import** (`VK_EXT_external_memory_dma_buf` + `VK_KHR_external_memory_fd`)
   — Linux GPU side only. Not applicable when the GPU side is Windows.
2. **`VK_KHR_external_memory_win32` — settled, and the answer is no.** A Win32
   section object from `CreateFileMapping` **cannot** be imported. The
   compatibility table in `chapters/capabilities.adoc` requires both
   `driverUUID` and `deviceUUID` to **match** for `OPAQUE_WIN32_BIT` and for all
   three D3D handle types, while `HOST_ALLOCATION_BIT_EXT` carries "no
   restriction" on either. `VUID-VkImportMemoryWin32HandleInfoKHR-handle-00659`
   adds that the memory "must have been created on the same underlying physical
   device as `device`". A `CreateFileMapping` section has no driverUUID or
   deviceUUID and was not exported by a Vulkan or D3D device. **`OPAQUE_WIN32`
   accepts only handles from `vkGetMemoryWin32HandleKHR`; the D3D types only
   handles from `CreateSharedHandle`. There is no Vulkan path on Windows for an
   arbitrary shared section.**

   Worth knowing as an aside: D3D12 *does* have the true analogue —
   `ID3D12Device3::OpenExistingHeapFromFileMapping` (and
   `OpenExistingHeapFromAddress` for a `VirtualAlloc` region) builds an
   `ID3D12Heap` directly from a file mapping. Both are documented as
   "special-purpose **diagnostic** heap[s]", and `shared-heaps.md` states
   "Shared heaps are not supported on CPU-accessible heaps", so bridging one
   into Vulkan via `D3D12_HEAP_BIT` is very likely impossible — **inference, not
   confirmed**. It would only be relevant if the GPU side were D3D12 rather than
   Vulkan on Windows, which is a different project.
3. **virtio-gpu blob resources** (`VIRTGPU_BLOB_MEM_GUEST`,
   `_HOST3D`, `_HOST3D_GUEST`) — **dead on Windows.** virtio-win's only GPU
   driver, `viogpudo`, is a display-only KMDOD that advertises exactly two
   feature bits (`VIRTIO_GPU_F_VIRGL`, `VIRTIO_GPU_F_EDID`) and contains no
   reference to blob resources at all. See §2.2.

**A distinction that decides the arena's home.** The extension defines **two**
handle types, and the spec is explicit that supporting one does not imply the
other:

| Handle type | Spec wording | Applies to |
|---|---|---|
| `HOST_ALLOCATION_BIT_EXT` | "a pointer to `allocationSize` number of bytes of **host memory**" | ordinary RAM — the AWE / guest-RAM arena |
| `HOST_MAPPED_FOREIGN_MEMORY_BIT_EXT` | "a pointer to `allocationSize` number of bytes of **host mapped foreign memory**" | device MMIO — an ivshmem BAR |

From the extension's issue resolutions:

> "8) Should we include the possibility to import host mapped foreign device
> memory using this API? RESOLVED: Yes, **through a separate handle type**.
> Implementations are still allowed to support only one of the handle types
> introduced by this extension by not returning import support for a particular
> handle type."

(`appendices/VK_EXT_external_memory_host.adoc`; the corresponding valid-usage
IDs are `VUID-VkImportMemoryHostPointerInfoEXT-handleType-01750/01751` in
`chapters/memory.adoc`.)

The spec also warns generally that "importing memory from a particular host
pointer **may not be possible due to additional platform-specific restrictions
beyond the scope of this specification**, in which case the implementation must
fail … with `VK_ERROR_INVALID_EXTERNAL_HANDLE_KHR`". So both candidate arenas
need an empirical test; the BAR-backed one needs the rarer handle type and is
the less likely to pass.

If none is available, the design degrades to §2.6 and the project's central
requirement is not met.

### 2.2 Q2 — Where does the arena physically live?

**The signing constraint is no longer a blocker.** A Microsoft-signed ivshmem
driver for Windows exists. This was verified by extracting `ivshmem.cat` from
the Looking Glass B7 host installer and parsing its PKCS#7 chain:

```
subject=CN=Microsoft Windows Hardware Compatibility Publisher
issuer =CN=Microsoft Windows Third Party Component CA 2014
         -> CN=Microsoft Root Certificate Authority 2010
```

That is exactly the chain Microsoft's policy requires for Windows 10 1607+ /
1803+ **with Secure Boot on**. `DriverVer 08/03/2022, 100.10.100.10000`, Red Hat
copyright, `[Standard.NTamd64.10.0]`, hardware IDs
`PCI\VEN_1AF4&DEV_1110&SUBSYS_11001AF4&REV_01` and the generic
`PCI\VEN_1AF4&DEV_1110` — so it binds to QEMU's `ivshmem-plain` regardless of
subsystem ID. The catalogue carries an RFC3161 countersignature (OID
`1.3.6.1.4.1.311.3.3.1`), so the signing certificate's 2023 expiry does not
invalidate it. **No test signing, no Secure Boot disable.**

Three corrections to widespread belief follow, all of which matter:

- **`ivshmem` is not in any current virtio-win build.** Grepping the zip central
  directories directly: `attestation-virtio-win-prewhql-0.1-302.zip` → **zero**
  occurrences of ivshmem across 80 `.inf` files; `virtio-win11-attestation-0.1-258.zip`
  → zero. Only the 2018-era `0.1-161` has one. Upstream issue
  <https://github.com/virtio-win/kvm-guest-drivers-windows/issues/1401> (opened
  2025-07-31, still open) asks Red Hat to refresh the signed build; it is
  blocked on <https://github.com/virtio-win/kvm-guest-drivers-windows/issues/1340>.
  **The Looking Glass installer is the only practical source.**
- **The driver the older Looking Glass docs point at is the wrong one.** The
  `virtio-win10-prewhql-0.1-161` ivshmem driver is signed `CN=Red Hat, Inc.` →
  `VeriSign Class 3 Code Signing 2010 CA`, `notBefore = Mar 18 2016` — a legacy
  cross-signed certificate issued *after* Microsoft's 29 July 2015 cutoff, so it
  will **not** load under Secure Boot. That is why the old instructions said to
  disable Secure Boot. Use the LG-bundled driver.
- **A signed Windows vsock driver also exists**, contrary to my expectation.
  `viosock` (`viosock.sys`, `viosock.cat`, `viosocklib_x64.dll`,
  `viosockwspsvc.exe`) ships in virtio-win build 0.1-302 with the same
  Microsoft WHCP chain as `netkvm.cat` and `vioser.cat`, binding
  `PCI\VEN_1AF4&DEV_1012`/`DEV_1053`. Per
  <https://github.com/virtio-win/kvm-guest-drivers-windows/issues/1185>,
  "Starting from virtio-win build 285, viosock driver is part of release".

So the drivers usable on this production Secure Boot guest with no signing work
are: **ivshmem** (via the LG installer), **vioser**, **viosock**, **netkvm** —
all Microsoft WHCP signed.

That said, the user's stated preference is to avoid a dedicated shared-memory
device if direct VM↔host mapping can be made to work, and that preference is
well-founded: it removes a device, a driver install, and a whole class of
caching problems. The two candidates are below, followed by the narrow question
that decides between them.

#### (a) An ivshmem BAR

QEMU spec (<https://raw.githubusercontent.com/qemu/qemu/master/docs/specs/ivshmem-spec.rst>):

> The Inter-VM shared memory device (ivshmem) is designed to share a memory
> region between multiple QEMU processes running different guests **and the
> host**. […] BAR2 maps the shared memory object.

and

> If you only need the shared memory part, BAR2 suffices. […] If you
> additionally need the capability for peers to interrupt each other, you need
> BAR0 and BAR1. **You will most likely want to write a kernel driver to handle
> interrupts.**

Status: only the *legacy* `ivshmem` device was removed (QEMU 4.0, per
`docs/about/removed-features.rst`). `ivshmem-plain` and `ivshmem-doorbell`
appear in neither `deprecated.rst` nor `removed-features.rst` and are confirmed
compiled into this machine's QEMU 10.2.2.

**Zero-copy is confirmed at source level**, not merely documented. From
`hw/misc/ivshmem-pci.c` (note: renamed from `ivshmem.c`):

```c
s->ivshmem_bar2 = host_memory_backend_get_memory(s->hostmem);
...
pci_register_bar(PCI_DEVICE(s), 2,
                 PCI_BASE_ADDRESS_SPACE_MEMORY |
                 PCI_BASE_ADDRESS_MEM_PREFETCH |
                 PCI_BASE_ADDRESS_MEM_TYPE_64,
                 s->ivshmem_bar2);
```

BAR2 **is** the memory backend's RAM `MemoryRegion` — not a copy, not a shadow.
The host process `mmap`s the same `/dev/shm` file or memfd; both sides touch
identical physical pages. It is 64-bit prefetchable, so multi-GB arenas are
fine.

**Crucially, the BAR is not treated as MMIO by KVM.** `__kvm_is_mmio_pfn()`
tests `PageReserved`, and `memory-backend-file`/`-memfd` pages are ordinary
RAM. So ivshmem BAR2 does *not* take the forced-uncacheable path that a real
device BAR takes in `vmx_get_mt_mask()`. This substantially weakens the concern
I had that a GPU driver would refuse to import it — from the CPU's and the
IOMMU's point of view these are normal RAM pages. It does not eliminate the
concern (see §2.2 residual unknowns), but it changes the prior.

**The caching default is a trap, and it is the one to get right.** Without the
`IPAT` bit, the guest's PAT wins, and the *default* for a PCI BAR under both
Windows and Linux is uncached. Accepting that default gives catastrophic
bandwidth. This is precisely why the virtio-win ivshmem driver's
`IVSHMEM_MMAP_CONFIG` takes a cache mode — `NONCACHED` / `CACHED` /
`WRITECOMBINED`. **You must explicitly request WB or WC.** The relevant KVM
code (`arch/x86/kvm/vmx/vmx.c`):

```c
if (is_mmio)
    return MTRR_TYPE_UNCACHABLE << VMX_EPT_MT_EPTE_SHIFT;
if (vmx_ignore_guest_pat(vcpu->kvm))
    return (MTRR_TYPE_WRBACK << VMX_EPT_MT_EPTE_SHIFT) | VMX_EPT_IPAT_BIT;
return (MTRR_TYPE_WRBACK << VMX_EPT_MT_EPTE_SHIFT);
```

with `vmx_ignore_guest_pat()` = `!kvm_arch_has_noncoherent_dma(kvm) &&
kvm_check_has_quirk(..., KVM_X86_QUIRK_IGNORE_GUEST_PAT)`. Whether the
passed-through iGPU forces guest-PAT-honouring depends on IOMMU snoop control
(`enforce_cache_coherency`); Raptor Lake VT-d supports it, so this machine
probably lands on the forced-WB path — but the quirk is recent and this is
**worth measuring rather than assuming**. Mesa's Venus documentation requiring
`-accel kvm,honor-guest-pat=on` for Intel hosts is evidence that this is a live
minefield.

**The structural limitation nobody documents clearly: you cannot have both your
own memory backend and hardware doorbell interrupts.**

- `ivshmem_plain_realize()` **requires** `memdev` and never sets `IVSHMEM_MSI`
  — **no interrupts at all**; you poll.
- `ivshmem_doorbell_realize()` **requires** `chardev` (a socket to
  `ivshmem-server`), sets `IVSHMEM_MSI`, and takes its memory *from the server*
  via `memory_region_init_ram_from_fd()`. **There is no `memdev` property on
  the doorbell variant.**

So doorbell means `ivshmem-server` owns the allocation. This is a real design
constraint and §7 works around it rather than fighting it.

**Measured performance** (*Secure IVSHMEM*, MemSys '25,
<https://arxiv.org/pdf/2505.19004>; Intel Core Ultra 7 155H, pinned vCPUs):
**8.1 µs** round trip for a 32-bit write *plus doorbell notification*;
~**3.0–3.5 GB/s** single channel at large messages; ~1.56 GiB/s per channel ×
8 channels ≈ **12.5 GiB/s** aggregate. Note the 8.1 µs is the *interrupt* path
— a polled ring in BAR2 is comfortably sub-microsecond, which is why Looking
Glass uses `ivshmem-plain` and spins.

**Windows user-mode API** (`ivshmem/Public.h`,
<https://github.com/virtio-win/kvm-guest-drivers-windows/blob/master/ivshmem/Public.h>):
device interface GUID `{df576976-569d-4672-95a0-f57e4ea0b210}`, IOCTLs
`REQUEST_PEERID`, `REQUEST_SIZE`, `REQUEST_MMAP`, `RELEASE_MMAP`,
`RING_DOORBELL`, `REGISTER_EVENT`, `REQUEST_KMAP`. Hard limit of 32 registered
events.

**But importing a BAR pointer as `VkDeviceMemory` is, on Linux, structurally
impossible — and that is strong evidence against it on Windows too.** The chain:

- PCI sysfs mmap uses `io_remap_pfn_range`, which stamps the VMA
  `VM_IO | VM_PFNMAP | VM_DONTEXPAND | VM_DONTDUMP`.
- `mm/gup.c`'s `check_vma_flags()` rejects exactly those:

  ```c
  	if (vm_flags & (VM_IO | VM_PFNMAP))
  		return -EFAULT;
  ```

  with `mm/memory.c` commenting "VM_IO is incompatible to GUP completely".
- Every driver implements `HOST_ALLOCATION` via kernel *userptr*, which pins
  with GUP or HMM. ANV goes to `DRM_IOCTL_I915_GEM_USERPTR`, whose kernel
  `probe_range()` comment is literally "Check that the range pointed to
  represents real struct pages and **not iomappings**"; on Xe it is
  `hmm_range_fault()`, same rejection. RADV goes to
  `amdgpu_create_bo_from_user_mem`.
- And `HOST_MAPPED_FOREIGN_MEMORY_BIT_EXT`, the handle type that *would* be
  spec-correct for a BAR, is supported by essentially nobody. ANV rejects it
  explicitly (`anv_device.c`):

  ```c
  if (mem->vk.import_handle_type ==
      VK_EXTERNAL_MEMORY_HANDLE_TYPE_HOST_MAPPED_FOREIGN_MEMORY_BIT_EXT) {
     result = vk_error(device, VK_ERROR_INVALID_EXTERNAL_HANDLE);
  ```

  RADV, lavapipe and dzn never mention it. AMDVLK advertises the path but PAL
  hardcodes `m_features.suportHostMappedForeignMemory = 0` on Linux. The only
  Mesa driver advertising it is kosmickrisp (Metal). NVIDIA proprietary is the
  one vendor where it is mechanically plausible, since its kernel driver has a
  real `VM_PFNMAP` path using `follow_pfnmap_start()` instead of GUP —
  **could not confirm** whether its ICD wires that up.

**The decisive corroboration is that Looking Glass's `kvmfr` module exists
precisely because this does not work.** Its documentation says the module
"allow[s] DMA GPU transfers" and that without it "you will not be able to take
advantage of your GPUs ability to access memory via it's hardware DMA engine".
What it actually does is call `devm_memremap_pages()` on BAR2 to **manufacture
`struct page`s for it**, mmap via a fault handler returning real pages so the
VMA is *not* `VM_PFNMAP`, and export the region as a **dma-buf**. The client
imports it through dma-buf, never as a host pointer.

I found **zero** reports of anyone successfully importing an ivshmem BAR pointer
into Vulkan via `VK_EXT_external_memory_host`. The CUDA analogue behaves the
same way — `cudaHostRegister` on `remap_pfn_range`d memory is a known open
regression, and CUDA has a *separate* `cudaHostRegisterIoMemory` flag for BAR
memory.

**Caveat on scope, stated plainly:** all of the above is the *Linux* kernel and
*Linux* driver path. On this machine the GPU side is **Windows**, where the
import path is WDDM/VidMm rather than GUP, so none of it is literally binding.
But the underlying reason generalises — GPU drivers pin pages, and BAR pages are
not normal pages — and Windows has its own version of the same rule
(`MmProbeAndLockPages` over device memory). **I would not bet on the Windows
path succeeding where every Linux path fails**, and it is cheap to test.

**Residual unknowns for ivshmem**, in order: (i) does
`vkGetMemoryHostPointerPropertiesEXT` return non-zero `memoryTypeBits` for a
pointer into the ivshmem mapping on Intel's *Windows* driver, and does the
subsequent `vkAllocateMemory` succeed; (ii) what is the effective memory type
under this machine's VFIO configuration, measured by raw memcpy bandwidth at
each of the three cache modes.

**If the arena must be a BAR, the only demonstrated-working design is Looking
Glass's**: a small kernel shim that `devm_memremap_pages()` the BAR and exports
a dma-buf, imported via `VK_KHR_external_memory_fd` +
`VK_EXT_external_memory_dma_buf`. That is a Linux-GPU-side answer, and it does
not help when the GPU side is Windows.

#### (b) The VM's own RAM

The guest already runs on `memory-backend-memfd,share=on` because virtio-fs
requires it, and under VFIO every guest page is pinned anyway. **So the Linux
side can already `mmap` the entire guest physical address space today, at zero
additional cost.**

The gfxstream investigation makes the same observation independently and calls
it the piece of luck in this topology: in QEMU, guest RAM *is* host memory, so
"one side's pages are visible to the other" is free in this direction.

**Strengths.** The arena is ordinary cached RAM. The GPU-side Windows driver
sees a perfectly normal host pointer, so `VK_EXT_external_memory_host` has the
best possible chance of accepting it, with normal write-back caching and normal
x86 coherency.

**Weakness — and the one genuinely open question in this document.** The
addressing problem moves to the Windows side. A user-mode process cannot
obviously tell the Linux side which guest-physical pages its allocation
occupies, and a user-mode virtual allocation is not physically contiguous.
Obtaining and pinning a guest-physical address is ordinarily kernel-mode work
(`MmAllocateContiguousMemory`, or non-paged pool plus `MmGetPhysicalAddress`),
which would reintroduce a bespoke driver.

**But it can be done from user mode, and this is now confirmed.**

#### Windows AWE returns real guest-physical frame numbers

`AllocateUserPhysicalPages` fills a `PageArray` that Microsoft's documentation
describes discouragingly — "Do not attempt to modify this buffer. It contains
operating system data… **The information in the buffer is not useful to an
application**"
(<https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-allocateuserphysicalpages>).
That is discouragement, not opacity. Microsoft's own released kernel source
settles it. From the Windows Research Kernel v1.2, `base/ntos/mm/physical.c`,
`NtAllocateUserPhysicalPages`:

```c
MemoryDescriptorList = MiAllocatePagesForMdl (..., MI_ALLOCATION_IS_AWE);
...
MdlPage = (PPFN_NUMBER)(MemoryDescriptorList + 1);
AllocatedPages = MemoryDescriptorList->ByteCount >> PAGE_SHIFT;
RtlCopyMemory ((PVOID) UserPfnArray, MdlPage, AllocatedPages * sizeof (PFN_NUMBER));
```

`MemoryDescriptorList + 1` is the MDL's PFN array, which by definition holds
physical frame numbers. **The user buffer receives a verbatim `RtlCopyMemory` of
MDL PFNs — no transformation, no indirection.** Three corroborations in the same
file: `NtMapUserPhysicalPages` validates returned frames against a bitmap
*indexed by physical frame number*
(`BitMapIndex = MI_FRAME_TO_BITMAP_INDEX(PageFrameIndex)`); it writes them
straight into hardware PTEs
(`NewPteContents.u.Hard.PageFrameNumber = PageFrameIndex`); and it dereferences
them into the PFN database (`MI_PFN_ELEMENT`).

Inside a VM, what the Windows kernel calls "physical" *is* guest-physical. So
`PageArray[i] << 12` is a QEMU GPA — exactly the index into the memfd.

The pages are locked: "After the memory is allocated, **it is locked down and
unavailable to the rest of the virtual memory management system**… it is never
paged – it is locked down until the application explicitly frees it or exits"
(<https://learn.microsoft.com/en-us/windows/win32/memory/address-windowing-extensions>).
The privilege is `SeLockMemoryPrivilege` ("Lock pages in memory"), a local
security-policy grant — the same one SQL Server has required for twenty years.
It does not touch code integrity, Secure Boot or test-signing. **The hard
constraint is untouched.** (You must also `AdjustTokenPrivileges` at runtime;
being granted it is not enough.)

**Documented AWE restrictions**, of which one matters:

- Not sharable with other processes, not inheritable; two AWE VAs in one process
  may not map the same physical page.
- "always read/write and **cannot be protected via calls to VirtualProtect**" —
  no guard pages, which incidentally rules out the dirty-tracking trick of §2.6
  on AWE memory.
- Cannot be split; `VirtualFree` must use `MEM_RELEASE`.
- **"AWE address ranges cannot be used to buffer data for graphics or video
  calls."**

That last line is the one real risk, and it is R19 below. It is old text — AWE
dates to Windows 2000 and the phrasing smells of GDI/DirectDraw — and it is
never qualified further. Counter-evidence that DMA from AWE is supported at the
kernel level: `MmProbeAndLockPages` has a dedicated AWE path setting
`MDL_DESCRIBES_AWE` and maintaining an `AweReferenceCount` per PFN
(WRK `base/ntos/mm/iosup.c`), so a driver *can* build an MDL over an AWE range
and DMA from it. Whether WDDM/VidMm's user-pointer import path chooses to accept
it is empirical.

**Contiguity is a non-problem, correctly reframed.** The docs warn to "make no
assumptions about the contiguity of the physical pages", but contiguity is
irrelevant when you are handed *every frame number*. The app side reconstructs a
contiguous virtual arena with N `mmap(MAP_FIXED)` calls into a pre-reserved
`PROT_NONE` range, one per contiguous run of memfd offsets — sort the PFN array
and coalesce runs first. The only real cost is VMA count: a 4 GiB arena is
1,048,576 pages against a default `vm.max_map_count` of 65530, so raise the
sysctl and rely on run-coalescing.

`MEM_LARGE_PAGES` does give physically contiguous 2 MiB blocks — architecturally
guaranteed, since a PDE-mapped page needs a 2 MiB-aligned contiguous frame — but
there is no user-mode way to learn a large page's physical address, so large
pages alone do not help. **Unconfirmed and worth ten minutes:** whether
`AllocateUserPhysicalPages2` accepts `MEM_EXTENDED_PARAMETER_NONPAGED_LARGE`
(0x08) to get large-page-backed AWE, which would deliver *both* the PFNs *and*
2 MiB contiguity and cut the VMA count 512×. The docs never enumerate which
extended-parameter types are valid.

No other documented user-mode Windows API surfaces a physical address.
`\Device\PhysicalMemory` has been closed to user mode since Server 2003 SP1.

#### GPA → memfd offset

*Corrected against the live machine (connected 2026-08-11): the VM is
`-machine pc,accel=kvm,smm=off` — **i440fx, not q35** — with `-m 13312`
(13 GiB) and its entire RAM is one `memory-backend-memfd,id=virtiofsmem,
size=13312M,share=on` attached as `-numa node,memdev=virtiofsmem`. So the
arena-in-guest-RAM premise is literally the status quo: the whole of guest RAM
is already a single shared memfd. Two of my earlier assumptions were wrong and
are fixed below.*

From `pc_memory_init()` (`hw/i386/pc.c`, v10.2.2), guest RAM is two aliases into
one backend: `ram-below-4g` at offset 0, and `ram-above-4g` at backend offset
`below_4g_mem_size` mapped at GPA `above_4g_mem_start`. An assertion guarantees
they tile the backend exactly:

```
GPA <  below_4g_mem_size   ->  offset = GPA
GPA >= above_4g_mem_start  ->  offset = GPA - above_4g_mem_start + below_4g_mem_size
```

**But `below_4g_mem_size` is computed differently on i440fx**, which is what
this machine uses. `pc_q35_init()`'s hardcoded `0x80000000` (my earlier text)
does *not* apply. On i440fx (`pc_piix.c` → `pc_init1`) the split is derived in
`x86ms->below_4g_mem_size` with the `gigabyte_align` machine-version compat knob
in play, so the boundary depends on RAM size and machine version and is **not** a
constant to hardcode. `above_4g_mem_start` still defaults to 4 GiB (relocated to
1 TiB only for large AMD guests — irrelevant here). **Do not hardcode the
below-4G size; read it.**

`memory-backend-memfd` creates a single memfd of exactly the backend size at fd
offset 0, and QEMU enforces `backend_size == ram_size`, so file offset and
region offset coincide. One content caveat: 0xa0000–0xfffff is shadowed by
VGA/PAM overlays. **There is no TSEG blackhole** — my earlier claim that TSEG is
live "because this guest uses VBS" was wrong on two counts: the machine runs
`smm=off`, so there is no SMRAM/TSEG at all, and TSEG would not have been
VBS-related regardless. Either way it does not matter, because Windows' PFN
database only ever contains E820-usable RAM.

At runtime the authoritative source is `info mtree -f`, whose flat view
*resolves aliases* and prints the terminal region plus its offset:

```
0000000000100000-000000007effffff (prio 0, ram): pc.ram @0000000000100000
0000000100000000-000000037fffffff (prio 0, ram): pc.ram @0000000080000000
```

The `@offset` is the memfd offset with overlays and any relocation already
accounted for. Reachable over QMP via
`human-monitor-command`. Note that `info ramblock`'s `Offset` column is a
`ram_addr_t`, **not** a GPA and not a file offset — its useful column is `HVA`.
No QMP command returns a machine-readable GPA→offset map, so parse
`info mtree -f` and cross-check against the closed form. Practically, open the
memfd through `/proc/<qemu-pid>/fd/<n>` rather than parsing `/proc/<pid>/maps`,
where every memfd backend appears under the literal name
`memory-backend-memfd` regardless of its object id.

#### Two options are now definitively dead

**Virtio shared memory regions: settled, not merely unlikely.** The virtio 1.2
spec §2.10 describes exactly the primitive we want, but the Windows
implementation cannot see it. `VirtIO/virtio_pci.h` defines cap types 1–5 only —
no `VIRTIO_PCI_CAP_SHARED_MEMORY_CFG`, no `virtio_pci_cap64` — and the
capability walker in `VirtIO/VirtIOPCIModern.c` **structurally cannot store one**:

```c
int capabilities[VIRTIO_PCI_CAP_PCI_CFG];   /* = int capabilities[5] */
...
if (bar < PCI_TYPE0_ADDRESSES && cfg_type < nOffsets && ...) { Offsets[cfg_type] = offset; }
```

A capability with `cfg_type == 8` is walked past and silently discarded.
Repo-wide grep for `SHARED_MEMORY_CFG`, `shmid`, `SHMEM`, `DAX`: zero hits
outside the unrelated `ivshmem/` directory. `viofs` is `viofs/pci/` (a thin KMDF
virtqueue transport) plus a WinFsp **user-mode** filesystem, with zero hits for
`dax|MmMapIoSpace|shm` — confirming the suspicion in §2.2 exactly. `viogpudo`
calls `DxgkInitializeDisplayOnlyDriver()` and defines only
`VIRTIO_GPU_F_VIRGL` and `VIRTIO_GPU_F_EDID` — no `RESOURCE_BLOB`, no
`CONTEXT_INIT`, zero hits for `blob`.

And there is no signed generic BAR-mapping driver to fall back on: that class
(WinRing0 and friends) is precisely what the **Microsoft Vulnerable Driver
Blocklist** blocks by default on Windows 11 whenever HVCI is on.

**`VHOST_USER_BACKEND_SHMEM_MAP`** (QEMU 11.1, verified absent in v11.0.0 and
present in v11.1.0) is therefore doubly useless here: not in 10.2.2, and it
installs host memory into a virtio shared memory region that no signed Windows
driver can consume.

**NVDIMM/DAX: three stacked unknowns — do not plan on it.** Windows does have
inbox signed NVDIMM support (`scmbus.sys`, `nvdimm.sys`, since 1607) and real
DAX volumes (`Format-Volume -IsDax:$true`) that give direct mapping of
memory-mapped files. But: (i) **no evidence in either direction** that a Windows
guest enumerates QEMU's emulated NFIT NVDIMM — every Windows vPMem reference
found concerns Hyper-V or ESXi, never QEMU/KVM; (ii) DAX volume creation is
documented as requiring Storage Spaces with a single PMEM disk, unclear on
client Windows 11; (iii) DAX pages are not ordinary PFN-database RAM, so Vulkan
import is a further unknown. Three gates, each able to kill it independently. A
two-hour spike could close the question; the architecture must not depend on it.

#### The verdict

| Rank | Option | Windows kernel driver | Signed & installable today | Address translation | Import as `VkDeviceMemory` | Residual unknown |
|---|---|---|---|---|---|---|
| **1** | **Guest RAM via AWE** | **None** — `SeLockMemoryPrivilege` only | n/a | Real guest PFNs, 4 KiB, scattered | **Best** — ordinary RAM, needs only `HOST_ALLOCATION_BIT_EXT` | The "no graphics or video calls" doc line (R19); Win11 24H2 still raw PFNs |
| **2** | **Attestation-signed bespoke pinning driver** | Yes, ~200 lines | You build it; MS signs it. **No test-signing.** | Free, any allocation | **Best** — plain `VirtualAlloc`, dodges every AWE restriction | EV cert friction; HVCI-clean build |
| 3 | ivshmem BAR2 (LG driver) | Yes | **Yes** — MS WHCP signed | **Free** (shared offsets) | **Probably not** — needs `HOST_MAPPED_FOREIGN_MEMORY_BIT_EXT`, which almost nobody implements; every Linux path is structurally blocked | Whether Windows/VidMm differs from Linux/GUP |
| 4 | NVDIMM + DAX volume | Inbox, if it works at all | Inbox | Free | Unknown | Three stacked unknowns |
| 5 | Virtio shmem region | Yes | **No — the code does not exist** | — | — | **None. Settled: dead.** |

**The ranking has changed twice, and the second change is the important one.** I
initially had ivshmem second on the strength of its signed driver. It belongs
third, and for a much harder reason than the one I first gave.

The first reason was that `VK_EXT_external_memory_host` defines *two* handle
types and the spec permits supporting only one — a BAR is *foreign mapped
memory* (`HOST_MAPPED_FOREIGN_MEMORY_BIT_EXT`), ordinary RAM is not
(`HOST_ALLOCATION_BIT_EXT`), and the former is rarer. That much stands.

The second and stronger reason is that the *mechanism itself* rules it out: host
pointer import is implemented as kernel userptr, userptr pins pages, and BAR
mappings are `VM_IO|VM_PFNMAP` which the page-pinning path rejects by
construction. Looking Glass had to write `kvmfr` — manufacturing `struct page`s
with `devm_memremap_pages()` and exporting dma-buf — precisely because of this.
**And Looking Glass's own track record does not cover our use case at all**: its
guest-side app `memcpy`s frames *into* the BAR. It never asks the GPU to DMA out
of it. So "ivshmem is proven by Looking Glass" is not evidence for what we need.

Meanwhile **attestation signing** deserves promotion to second, because it is a
better fallback than I credited. It is not test-signing: an EV code-signing
certificate plus a Partner Center submission yields a genuine Microsoft
signature that loads on retail Windows 11 with Secure Boot and HVCI on
(<https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation>).
The driver needed is trivial — `MmProbeAndLockPages` on a user VA, walk
`MmGetMdlPfnArray`, copy out — and it makes any ordinary `VirtualAlloc` buffer
work, dodging every AWE restriction including the graphics one, and dodging the
"are modern PageArray values still raw PFNs" question entirely. The cost is an
EV certificate and some bureaucracy, not a technical blocker.

So the shape is: **AWE if it works; an attestation-signed 200-line pinning
driver if it does not; ivshmem only as a last resort and probably not at all.**
Note that both of the top two options land the arena in **ordinary guest RAM**,
which is also the only kind of memory the import mechanism actually likes. The
two lines of reasoning — "which pages can the two sides agree on" and "what will
the driver import" — converge on the same answer, which is reassuring.

**And the cross-platform corollary, which is a design requirement rather than a
detail:** because RADV refuses every shared mapping (§2.1) and because a Linux
GPU side may be AMD, **the arena import path has to be pluggable from the
start** — `VK_EXT_external_memory_host` where it works, dma-buf
(`VK_KHR_external_memory_fd` + `VK_EXT_external_memory_dma_buf`) on
AMD/Linux. The brief requires either side to be either OS, so this is not
optional.

### 2.3 Q3 — Coherency

**With a genuine shared mapping of ordinary RAM, on x86, there is nothing to
do.** Both sides map the same physical pages through different page tables;
x86 cache coherency is maintained in hardware; ordinary acquire/release
ordering suffices. This is why Venus's vtest `bo_flush`/`bo_invalidate` are
`/* nop */` and why gfxstream has **no** `on_vkFlushMappedMemoryRanges` in its
app-side resource tracker at all (confirmed by grep: zero hits) — it forwards
the call as an ordinary command and relies on the sharing being real.

The caveats are about *caching attributes*, not coherency:

**What gfxstream does.** The GPU side tags each allocation with a caching mode
derived from the Vulkan memory property flags and reports it back:
`HOST_CACHED → MAP_CACHE_CACHED`, `DEVICE_UNCACHED_AMD → MAP_CACHE_UNCACHED`,
**`HOST_COHERENT → MAP_CACHE_WC`** (write-combining). QEMU passes it through
(`resp.map_info = map_info & RUTABAGA_MAP_CACHE_MASK`) and the guest kernel
picks the PTE cacheability. So the caching attribute is *negotiated per
allocation and driven by the memory type*, not fixed globally.

**This is the correct answer to the sharedgl criticism in the requirement
document.** sharedgl maps its whole region `WRITECOMBINED` — right for a pure
producer, wrong for a consumer. The fix is not to pick the other one; it is to
make it **per-allocation and derived from the advertised memory type**, exactly
as gfxstream does:

- Memory the app writes and the GPU reads (staging, uniforms, vertex/index
  streaming) → advertise `HOST_VISIBLE | HOST_COHERENT` and map **WC** on the
  app side. Writes are fast and go straight out; the application is not
  supposed to read it back.
- Memory the app reads back (query results, readback buffers) → advertise
  `HOST_VISIBLE | HOST_COHERENT | HOST_CACHED` and map **WB**. Reads are fast.
  This is the standard Vulkan idiom and applications already select on
  `HOST_CACHED` for readback.

Our inversion swaps which *machine* is the producer, but not which *memory
type* is which — the Vulkan memory-type table is expressed in terms of the
application, and the application is on the app side in both topologies. So the
usual mapping still applies.

**The x86 aliasing caveat**, which is real and must be respected: mapping the
same physical page with two different cache attributes from two different page
tables is architecturally undefined on x86 and can cause genuine corruption.
If the app side maps a region WC, the GPU side must not map the same pages WB.
Keep the attribute a property of the arena *sub-region*, agreed at allocation
time and identical on both sides. QEMU's `honor-guest-pat=on` (which Mesa's
Venus documentation notes is needed for some configurations) exists because of
exactly this class of problem; if we end up needing it, that is a signal we
have got the attribute negotiation wrong.

**When flush/invalidate become real operations.** Only in the degraded mode of
§2.6, or if the transport ever spans two physical machines. In the arena
design they remain nearly free, and honesty is preserved because we are not
lying: the memory genuinely is coherent.

### 2.4 Q4 — What to advertise in `vkGetPhysicalDeviceMemoryProperties`

This table is the steering wheel: get it right and applications take the fast
path without being asked. The design:

| Heap | Type flags | Backing | Purpose |
|---|---|---|---|
| Heap 0 — device | `DEVICE_LOCAL` | Real GPU-side memory, never mapped | Render targets, textures, everything the app does not map. Filled by ordinary Vulkan transfer commands from arena-backed staging. |
| Heap 1 — arena | `DEVICE_LOCAL \| HOST_VISIBLE \| HOST_COHERENT` | Arena, mapped WC app-side | The "BAR"/upload type. On a UMA iGPU this is honest — it genuinely is device-local. |
| Heap 1 — arena | `HOST_VISIBLE \| HOST_COHERENT` | Arena, mapped WC app-side | Staging/upload for the non-UMA case. |
| Heap 1 — arena | `HOST_VISIBLE \| HOST_COHERENT \| HOST_CACHED` | Arena, mapped WB app-side | Readback. |

Three points that make this work:

1. **Ordering matters and is spec-constrained.** Verbatim from `memory.adoc`:

   > For each pair of elements *X* and *Y* returned in `memoryTypes`, *X*
   > must: be placed at a lower index position than *Y* if:
   > - the set of bit flags returned in the `propertyFlags` member of *X* is a
   >   strict subset of the set of bit flags returned in the `propertyFlags`
   >   member of *Y*; or
   > - the `propertyFlags` members of *X* and *Y* are equal, and *X* belongs to
   >   a memory heap with greater performance

   with a note that there is **no** ordering requirement when the flags are not
   in a subset relation, so more than one valid order exists. Applications
   iterate and take the *first* match, so within that freedom the order
   determines what they get: put the choice we want taken first.
2. **The arena heap's `size` should be the real arena size**, not a fiction.
   Applications use heap size for budgeting and `VK_EXT_memory_budget`; lying
   produces allocation failures at bad moments.
3. **The `DEVICE_LOCAL | HOST_VISIBLE` type is what makes applications do the
   right thing.** DXVK, vkd3d and modern engines specifically look for it
   (the "ReBAR" type) and will stream directly into it. On an Intel iGPU,
   where system RAM *is* device memory, advertising it is not a lie.

Anything that cannot be arena-backed — sparse/aliased resources, images with
optimal tiling, anything the GPU-side driver insists on placing itself — stays
in heap 0 and moves by `vkCmdCopyBufferToImage` and friends from arena staging.
That is exactly the data flow real applications already use, so the fast path
and the natural path coincide.

### 2.5 Q5 — Lifetime (a correctness question, not a security one)

Per `security-model.md`, **this is not a security boundary** and must not be
described as one. Nothing below is proposed as a defence against a hostile
peer; copying, revalidation and shadow buffers are explicitly off the table
because they would defeat the arena.

**On whether validation would be theatre: the reasoning holds, and I agree with
it.** The argument in `security-model.md` is correct and worth stating in its
strongest form. The arena is memory both sides map writably and concurrently.
Any property the GPU side checks — an offset within bounds, a size, a
descriptor's contents, a `sType` — can be changed by the app side between the
check and the driver's use of it, and the window is not small: the GPU may read
the memory milliseconds later, asynchronously, via DMA. This is a
time-of-check/time-of-use race *by construction*, not by implementation
weakness. The only way to close it is to copy into memory the app side cannot
reach, which is precisely the design we are told not to build. So a design that
validates and then advertises itself as safe would be making a claim it cannot
support. Documenting the exposure is the honest option, and it is the one
taken.

Two refinements worth adding to that reasoning, because they sharpen where the
line actually falls:

- The argument applies to *data the GPU reads later*. It does **not** apply to
  values the GPU side reads once, copies into its own stack or heap, and then
  uses — e.g. a command opcode, an array count used to size a local loop, a
  handle index resolved through a table. Those are already snapshotted by the
  act of reading them, so a bounds check on them is *not* theatre; it is an
  ordinary check on a local variable. This is the category where cheap checks
  genuinely buy correctness, and it happens to be most of the decoder.
- The distinction that matters is therefore not "trusted vs untrusted" but
  **"is this value still in the arena when it is used?"** Values that are get
  no meaningful protection; values that have been pulled out do. Worth encoding
  that as a decoder convention rather than rediscovering it per call site.

**What to take, because it costs nothing and catches our own bugs:**

- **Boxed handles** (§1.3) — required for correctness regardless, since the two
  sides do not share an address space and a `VkDeviceMemory` on one side is a
  suballocation on the other. A `SlotMap<Key, HandleInfo>` with a per-type tag
  gives handle→object resolution, dispatch attachment, ordering state and
  deferred destruction in one structure. Take it in full; it is not a security
  measure here, it is the object model.
- **Bounds-check offsets against the region length.** One compare. The
  realistic failure it catches is a generator bug producing a wrong `len=`
  expression, which is risk R8 and by far the most likely way this project
  corrupts memory.
- **Length-prefixed pNext links with a 0 terminator** (§1.3) — so the decoder
  can traverse a chain without trusting any pointer or needing the full type
  table. Again, correctness first: it makes forward/backward compatibility
  between mismatched builds a defined behaviour rather than a crash.
- The **strict-server / lenient-client** asymmetry gfxstream uses for unknown
  structures is worth keeping, but for a different reason than gfxstream's: a
  fatal abort on the GPU side turns a silent protocol mismatch into a loud one,
  which is what we want from a debugging standpoint.

**`vkFreeMemory` while the GPU may still be reading.** Vulkan's own rules
already require the application not to free memory in use by pending command
buffers, so the *application-facing* contract is not our problem. Our problem
is that the app side and the GPU side disagree about *when* work has retired,
and the app side's allocator must not hand a region out again while the GPU is
still DMAing from it. Three mechanisms, all present in the prior art:

1. **Deferred destruction.** gfxstream's `BoxedHandleManager::removeDelayed(h,
   device, callback)` keeps the GPU-side mapping alive until the GPU is
   genuinely done, invisibly to the app side. Arena sub-allocations must not be
   returned to the allocator until the same point.
2. **Retirement by timeline seqno.** Tag each arena sub-allocation with the
   value of the queue timeline at which it becomes free; the allocator reclaims
   only once the GPU-side timeline has passed it. This is `vn_ring_wait_seqno`
   / the ASG seqno mechanism applied to memory lifetime.
3. **A handshake word for in-flight buffers.** gfxstream's
   `CommandBufferStagingStream` uses an 8-byte
   `kSyncDataReadPending`/`kSyncDataReadComplete` word in the shared region
   precisely so the app side does not free a buffer the GPU side is still
   reading. Cheap and effective.

**Against a crashed app side.** The GPU side must survive the app side
vanishing mid-ring. Venus's `VK_RING_STATUS_ALIVE_BIT_MESA` and
`maxReportingPeriodMicroseconds` (in `VkRingMonitorInfoMESA`) exist for this:
a liveness heartbeat in the shared region with a timeout. On timeout, tear down
the context, destroy all its boxed handles and free its arena region. A
generation counter in the control region's handshake header lets a reconnecting
app side be distinguished from the dead one.

**Against a crashed GPU side.** Symmetrically, the app side must fail cleanly:
`VK_RING_STATUS_FATAL_BIT_MESA` and a liveness timeout, after which every
outstanding call returns `VK_ERROR_DEVICE_LOST`. That is the spec-sanctioned
way to say "your GPU went away" and applications are required to handle it.

### 2.6 If the arena proves impossible — the degraded mode, and its limits

Recorded for completeness and as the fallback if driver signing blocks
everything. It is *not* a recommendation.

Two legal sync points let a copying implementation be *correct*, if slow:

**App writes → GPU.** From `Vulkan-Docs/chapters/synchronization.adoc`
(lines 8398-8408):

> The first synchronization scope includes execution of flink:vkQueueSubmit on
> the host and anything that happened-before it, as defined by the host memory
> model.

So writes to coherent mapped memory before `vkQueueSubmit` are required to be
visible to the device *because of* the submit. **Shipping dirty pages at submit
time is therefore correct**, not a hack. (The same section notes non-temporal
stores are outside the host memory model and are the application's problem —
we inherit that caveat rather than owning it.)

**GPU writes → app.** Symmetrically, the app is only entitled to see device
writes after a fence or semaphore wait completes, so pulling memory back at
that point is the corresponding correct moment.

Implementation: return a shadow buffer from `vkMapMemory`; track dirty pages
with `mprotect`+`SIGSEGV` on Linux or `GetWriteWatch` with `MEM_WRITE_WATCH` on
Windows (much cheaper than exception handling, and purpose-built for this);
flush dirty ranges on submit, pull back on fence completion.

Costs and holes: a page fault per first write per page per frame for streaming
buffers; bandwidth proportional to the dirty set rather than the useful set; a
large persistently-mapped staging buffer degenerates to shipping the whole
thing. And two hard defeats: **`VK_KHR_buffer_device_address`**, where the app
writes a raw 64-bit address into a buffer for a shader to dereference with no
host-side call to intercept, and **`VK_EXT_descriptor_buffer`**, where
descriptors are written straight into mapped memory. See §5 for who requires
these.

This mode is probably adequate for Zink and definitely inadequate for
vkd3d-proton.

### 2.7 Large resource transfer

With the arena, this problem disappears: the application writes into arena
memory that is already `VkDeviceMemory` on the GPU side, and the command stream
carries offsets. Nothing marshals payload. That is the whole point of the
requirement.

For the residual cases — images with optimal tiling that must live in GPU-side
memory — the flow is arena staging buffer → `vkCmdCopyBufferToImage`, i.e.
ordinary Vulkan, executed entirely on the GPU side. Venus needed an explicit
fallback for when even that was unavailable
(`vkCopyMemoryToImageMESA` / `vkCopyImageToMemoryMESA` with an inline
`pData`/`dataSize` blob); we should define the equivalent but expect it to be
cold-path only.

### 2.8 Presentation

The one place where this topology is **strictly worse** than the conventional
one. In virtio-GPU the app side is in the guest and the *host* displays, so the
finished frame is already where the screen is. For us the frame must cross the
boundary every frame, forever.

gfxstream's lesson is instructive and slightly liberating: **it never forwards
`VK_KHR_swapchain` at all.** Confirmed by grep — zero occurrences of
`vkCreateSwapchainKHR` or `vkQueuePresentKHR` in `VkEncoder.cpp`. Presentation
is deliberately *outside* the serialised protocol; the app side uses Mesa's
generic WSI and swapchain images are dma-buf-exported blob resources handed to
the host compositor, or on Android `VK_ANDROID_native_buffer`. **Do not try to
solve presentation inside the protocol.**

The good news is that our exact problem — GPU in the VM, display outside — is
solved in production by **Looking Glass** (<https://looking-glass.io/>):

> Looking Glass does not use any form of compression or color space conversion,
> all frames are transferred to the viewer (client application) in 32-bit RGBA
> without any transformations or modifications. This is possible through the
> use of a shared memory segment which enables extremely high throughput low
> latency guest to host communication.

Licence **GPL-2.0** — study the architecture, do not lift code into a permissive
project.

| Option | Mechanism | 1080p60 / 4K60 | Latency | Notes |
|---|---|---|---|---|
| Uncompressed via arena | GPU side blits swapchain image to a linear buffer in the arena; app side presents | 8.3 MB/frame → **~500 MB/s** / ~2 GB/s | Sub-frame | Looking Glass's approach; needs the arena anyway |
| Uncompressed via socket | Same, copied over TCP | Same, now on the wire (~4 Gbit/s at 1080p60) | +copy | Plausible on virtio-net, hopeless on virtio-serial |
| Hardware video encode | Intel QuickSync on the GPU side, decode app-side | 10–50 Mbit/s | +≥1 frame | The Sunshine/Moonlight model; lossy; right for a genuinely remote app side |
| Damage-tracked / tiled | Ship changed tiles only | Workload-dependent | Variable | Big win for desktop/GUI, none for a game |

A wrinkle specific to us: the app side here has **no GPU**, so whatever it does
to get pixels on screen runs on llvmpipe. A full-screen RGBA blit per frame in
software is fine, but it is not free and rules out anything clever app-side.

Recommended shape: implement `VK_KHR_swapchain` app-side, backing its images
with GPU-side `VkImage`s; on `vkQueuePresentKHR` issue a GPU-side copy into a
linear arena buffer and signal the app side. Encode-and-stream only for remote
app sides.

### 2.9 Synchronisation

Venus's model, from `vn_renderer.h`, is the right primitive and is
direction-neutral:

> A sync consists of a uint64_t counter. The counter can be updated by CPU or
> by GPU. It can also be waited on by CPU or by GPU until it reaches certain
> values. This models after timeline VkSemaphore rather than timeline
> drm_syncobj.

**Model everything as a monotonic 64-bit timeline** — i.e.
`VK_SEMAPHORE_TYPE_TIMELINE`, core in Vulkan 1.2. Binary semaphores and fences
are expressible on top of timelines; the reverse is not.

- **Semaphores used only between GPU-side queues never cross the boundary.**
  Encode the submit and let the real driver handle it. That is the
  overwhelming majority of synchronisation in a real application, and it costs
  us nothing.
- **Fences and host waits do cross.** Both Venus (`vkWaitRingSeqnoMESA`,
  per-queue timeline bound to a `ring_idx` via `VkDeviceQueueTimelineInfoMESA`)
  and gfxstream (shared-memory seqno word) solve it the same way: **the counter
  lives in the shared control region**, so the app side polls a local load
  rather than making a round trip. With the arena this is sub-microsecond.
- **`vkGetSemaphoreCounterValue` in a polling loop** is the pathological case
  and is exactly why the counter must be mirrored into shared memory.
- **External semaphores/fences** are in the "not serializable" bucket per the
  Venus wire spec. Both projects punt: Venus with
  `vkImportSemaphoreResourceMESA` (import by resource id, not by handle),
  gfxstream with a frankly comical OPAQUE_FD fallback where the GPU side's
  integer fd number is written into an anonymous file app-side as a cookie. We
  should simply not advertise external handle types we cannot honour, which is
  legal.

**gfxstream's sync layer does not transfer to us and must be rewritten.** It is
built end to end on the GPU side creating host-kernel fence objects that the
VMM converts into guest-kernel fence objects (`sync_fd`/`dma_fence`,
virtio-gpu `(ring_idx, fence_id)`, `VirtioGpuTimelines`) — another host→guest
primitive. Our replacement is shared-memory timeline words plus a doorbell,
which is simpler, but it is new code.

**The one non-negotiable optimisation:** `vkQueueSubmit` must be
**asynchronous** — encode and return. Venus does this (only commands with
`VK_COMMAND_GENERATE_REPLY_BIT_EXT` block) and gfxstream invented
`vkQueueSubmitAsyncGOOGLE` for it. If submit is synchronous the design is dead
on latency grounds regardless of transport.

## 3. The app-side entry point: an ICD, not a layer

### 3.1 Verdict first

**Implement an ICD.** A layer cannot work here, for three independent and
decisive reasons:

1. **A layer is never the terminator.** From `LoaderInterfaceArchitecture.md`:
   "for functions in the instance call chain, the loader has an additional
   function, called a terminator, which is called after all enabled layers to
   marshall the appropriate information to all available drivers", and "This
   allows for the specific driver exposing this device to always be the
   terminator of the [device] chain." A layer sits *above* the terminator by
   construction and has nowhere to route a `VkDevice` call except down to a real
   driver.
2. **Zero drivers means `vkCreateInstance` fails outright.** `loader/loader.c`:

   ```c
   if (VK_SUCCESS == res && (ptr_instance->icd_terms == NULL || !one_icd_successful)) {
       loader_log(..., "terminator_CreateInstance: Found no drivers!");
       res = VK_ERROR_INCOMPATIBLE_DRIVER;
   }
   ```

   On a machine with no GPU our layer's call-down returns
   `VK_ERROR_INCOMPATIBLE_DRIVER` and there is nothing to be done about it.
3. **Physical device enumeration is aggregated by the loader across ICDs.** A
   layer can filter or reorder results; it cannot conjure a `VkPhysicalDevice`
   that `loader_physical_device_term` will accept, because those wrappers are
   minted by the terminator from ICD-returned handles.

A layer is the right tool only when a real local driver exists underneath — the
opposite of our situation.

Sources (all fetched raw):
<https://raw.githubusercontent.com/KhronosGroup/Vulkan-Loader/main/docs/LoaderDriverInterface.md>,
`LoaderLayerInterface.md`, `LoaderInterfaceArchitecture.md`, and
<https://raw.githubusercontent.com/KhronosGroup/Vulkan-Headers/main/include/vulkan/vk_icd.h>
(`SPDX-License-Identifier: Apache-2.0 OR MIT`, so its contents may be freely
re-expressed in Rust).

Useful third option **for testing only**: `VK_LUNARG_direct_driver_loading`,
where the application passes `VkDirectDriverLoadingListLUNARG` with our
`pfnGetInstanceProcAddr` in `VkInstanceCreateInfo::pNext`. No manifest, no
install, works under elevated privileges. Interface version 7 exists partly to
support it.

### 3.2 Linux mechanics

**Manifest search paths.** The loader appends `/vulkan/icd.d` to each of:
`$XDG_CONFIG_HOME` (or `$HOME/.config`), `$XDG_CONFIG_DIRS` (or `/etc/xdg`),
`SYSCONFDIR` (`/etc`), `EXTRASYSCONFDIR`, `$XDG_DATA_HOME` (or
`$HOME/.local/share`), `$XDG_DATA_DIRS` (or `/usr/local/share/:/usr/share/`).
The `$HOME`-derived ones are **ignored under elevated privileges**. Within a
directory the read order is `readdir` order — effectively random, so never rely
on ordering. The filename is arbitrary; only the `.json` suffix matters.

**Environment variables** — get this right, because the obvious one is
deprecated:

| Variable | Status | Semantics |
|---|---|---|
| **`VK_DRIVER_FILES`** | **current** | Overrides all default discovery. Colon-separated on Linux, semicolon on Windows. Files or directories. |
| `VK_ICD_FILENAMES` | **deprecated** | Same behaviour; **ignored if `VK_DRIVER_FILES` is set**. |
| `VK_ADD_DRIVER_FILES` | current | *Adds* to the standard search; not used if either of the above is set. |

Also `VK_LOADER_DRIVERS_SELECT` / `_DISABLE` (glob patterns, loader ≥ headers
1.3.234). The documentation names `VK_DRIVER_FILES` as *the* supported
mechanism for a driver in a developer build tree — exactly our dev loop.

**Manifest schema.** Only `file_format_version` 1.0.0 and 1.0.1 exist.

```json
{
   "file_format_version": "1.0.1",
   "ICD": {
      "library_path": "path to driver library",
      "api_version": "1.2.205",
      "library_arch": "64",
      "is_portability_driver": false
   }
}
```

`library_path`: a bare filename resolves via the OS search path; a relative path
resolves **relative to the JSON file**; absolute is used as-is. `library_arch`
and `is_portability_driver` were added in 1.0.1.

**An `api_version` trap that will bite.** The loader decides whether we are a
"1.0 driver" by reading `api_version` from the JSON, then — if ≥ 1.1 —
`dlopen`ing us and calling `vkGetInstanceProcAddr(NULL,
"vkEnumerateInstanceVersion")`. We get demoted to a 1.0 driver, **and every
`VkApplicationInfo::apiVersion` we receive is rewritten to 1.0**, if the JSON
says < 1.1, *or* that function pointer is NULL, *or* it returns < 1.1, *or* it
returns anything but `VK_SUCCESS`. So: ship a real `api_version` **and**
implement `vkEnumerateInstanceVersion`.

**Do not set `is_portability_driver`** unless the remote device genuinely
exposes `VK_KHR_portability_subset`. The loader "does not load any drivers that
declare themselves to be portability drivers" unless the application sets
`VK_INSTANCE_CREATE_ENUMERATE_PORTABILITY_BIT_KHR` — setting it makes us
invisible to every application that has not opted in.

**Required exports:**

```c
VKAPI_ATTR PFN_vkVoidFunction VKAPI_CALL vk_icdGetInstanceProcAddr(VkInstance, const char*);
VKAPI_ATTR VkResult VKAPI_CALL vk_icdNegotiateLoaderICDInterfaceVersion(uint32_t* pSupportedVersion);
PFN_vkVoidFunction vk_icdGetPhysicalDeviceProcAddr(VkInstance, const char*);
// Windows only:
VKAPI_ATTR VkResult VKAPI_CALL vk_icdEnumerateAdapterPhysicalDevices(
    VkInstance, LUID adapterLUID, uint32_t* pPhysicalDeviceCount, VkPhysicalDevice*);
```

`vk_icdGetInstanceProcAddr` must handle a **NULL `VkInstance`** for global-level
lookups. Two rules that matter for a Rust `cdylib`:

> "All other Vulkan entry points must either: NOT be exported directly from the
> driver library, or NOT use the official Vulkan function names if they are
> exported."

> "On Linux, if official names are used, the driver library must be linked with
> `-Bsymbolic`."

Mesa does exactly this (`gnu_symbol_visibility: 'hidden'` + `ld_args_bsymbolic`
+ a version script). In Rust: `#[no_mangle] pub unsafe extern "system"` on the
four `vk_icd*` symbols, plus `-C link-arg=-Bsymbolic` and a version script if
anything else is exported.

**Loader/driver interface versions**, since the numbers are otherwise opaque:

| Ver | What it adds |
|---|---|
| 0 | No `vk_icd*` at all; driver exports real Vulkan names |
| 1 | Adds `vk_icdGetInstanceProcAddr` |
| 2 | Adds the negotiate function. **Also where the dispatchable-object magic value becomes mandatory.** |
| 3 | Driver may create/destroy its **own** `VkSurfaceKHR` (opt-in: opt out by not exposing `vkCreateXXXSurfaceKHR`) |
| 4 | Adds `vk_icdGetPhysicalDeviceProcAddr` for unknown physical-device entry points. Required if we expose any physical-device extension the loader does not know, else it misclassifies them as device functions |
| 5 | **No interface change** — a signal that the *loader* now validates `apiVersion`. At ≤ 4 the **driver** must fail `apiVersion > 1.0` itself |
| 6 | Adds `vk_icdEnumerateAdapterPhysicalDevices` (Windows). The loader only sorts physical devices for drivers at ≥ 6 |
| 7 | **Relaxes exports** — the negotiate / physical-device / adapter functions need only be queryable through `vk_icdGetInstanceProcAddr` (as *global* functions, with NULL instance) |

`CURRENT_LOADER_ICD_INTERFACE_VERSION` is 7. Negotiation: the loader passes its
maximum, we clamp downward and return `VK_SUCCESS`. **Target 7, be prepared to
operate at 5.**

### 3.3 The dispatchable-handle trap — the thing to get right on day one

Every dispatchable object we return (`VkInstance`, `VkPhysicalDevice`,
`VkDevice`, `VkQueue`, `VkCommandBuffer`) must be a real pointer to a structure
whose **first pointer-sized field** we initialise to `ICD_LOADER_MAGIC`. From
`vk_icd.h`:

```c
#define ICD_LOADER_MAGIC 0x01CDC0DE
typedef union { uintptr_t loaderMagic; void *loaderData; } VK_LOADER_DATA;
static inline void set_loader_magic_value(void *pNewObject) {
    ((VK_LOADER_DATA *)pNewObject)->loaderMagic = ICD_LOADER_MAGIC;
}
```

What the documentation under-sells, and the loader source makes explicit
(`loader/loader.h`):

```c
static inline void loader_set_dispatch(void *obj, const void *data) { *((const void **)obj) = data; }
static inline void loader_init_dispatch(void *obj, const void *data) {
#if defined(DEBUG)
    assert(valid_loader_magic_value(obj) && "Incompatible ICD, first dword must be initialized to ICD_LOADER_MAGIC...");
#endif
    loader_set_dispatch(obj, data);
}
```

**The loader overwrites that word with its own dispatch-table pointer.** We lose
those 8 bytes permanently: never store anything there, never read it back. And
the assertion is **debug-only**, so getting it wrong usually manifests as a
segfault inside the loader rather than a clean error.

Non-dispatchable handles (`VkBuffer`, `VkImage`, …) are plain `u64` and are ours
to define however we like — which is where the object-id scheme of §4 lives.

**The Rust idiom**, from Kazan (`vulkan-driver/src/handle.rs`):

```rust
#[repr(C)]
pub struct DispatchableType<T> { loader_dispatch_ptr: usize, value: T }
impl<T> From<T> for DispatchableType<T> {
    fn from(v: T) -> Self { Self { loader_dispatch_ptr: ICD_LOADER_MAGIC as usize, value: v } }
}
impl<T> Deref for DispatchableType<T> { type Target = T; fn deref(&self) -> &T { &self.value } }
```

with `HandleAllocFree::allocate` = `Box::into_raw(Box::new(v.into()))`.
Rust-specific hazards beyond the C ones:

- `#[repr(Rust)]` gives no field-order guarantee. **`#[repr(C)]` is mandatory**
  and the magic field must be declared first.
- Do not use `Box<dyn Trait>` — and more importantly do not use **`Arc<T>`** as
  the handle: `Arc`'s allocation begins with the strong/weak counts, so offset 0
  is not ours.

### 3.4 WSI — what the driver must implement

`VK_KHR_surface` is instance-level and **loader-owned**. `VK_KHR_swapchain` is
device-level and **always driver-owned**.

By default (interface ≤ 2, or opting out) the loader creates the surface itself
and hands us a `VkIcdSurfaceXXX` from `vk_icd.h` — `VkIcdSurfaceXlib`,
`VkIcdSurfaceXcb`, `VkIcdSurfaceWayland`, `VkIcdSurfaceWin32` — each beginning
with `VkIcdSurfaceBase { VkIcdWsiPlatform platform; }`. We cast it.

We must implement regardless, because these take a physical device or device:
`vkGetPhysicalDeviceSurfaceSupportKHR`, `…SurfaceCapabilitiesKHR`,
`…SurfaceFormatsKHR`, `…SurfacePresentModesKHR` (and `2KHR` variants), the
`…PresentationSupportKHR` family, and all of `VK_KHR_swapchain`.

A silent-failure trap worth knowing: in `loader/wsi.c`,
`terminator_CreateSwapchainKHR` with a NULL driver function pointer logs and
**returns `VK_SUCCESS` with an uninitialised swapchain**.

**For us, `VK_EXT_headless_surface` is very likely the right answer** — the
loader has `terminator_CreateHeadlessSurfaceEXT`, and presentation happens
GPU-side anyway (§2.8), so remoting an X11/Wayland surface handle would be
effort spent to reach a worse design.

**One hard limit to note:** `loader/vk_loader_platform.h` has
`#define MAX_NUM_UNKNOWN_EXTS 250`, with 250 hand-generated trampolines. Since
we will mirror whatever the remote GPU exposes, and the loader's
known-extension list depends on the *loader's* header version, an older loader
could plausibly hit this ceiling.

### 3.5 Windows mechanics

Two discovery mechanisms. The PnP one reads `VulkanDriverName` (and
`VulkanDriverNameWow`) from
`HKLM\System\CurrentControlSet\Control\Class\{Adapter GUID}\000X` — path-valued,
tied to a device. The one we want is the global key:

```
HKEY_LOCAL_MACHINE\SOFTWARE\Khronos\Vulkan\Drivers
HKEY_LOCAL_MACHINE\SOFTWARE\WOW6432Node\Khronos\Vulkan\Drivers   (32-bit apps)
```

> "Every driver in these locations should be given as a **DWORD, with value 0**,
> where the name of the value is the full path to a JSON manifest file."

Value `0` = load, non-zero = disabled.

**A device-less software ICD is explicitly supported**, not a hack. The
documentation says so directly:

> "The `SOFTWARE\Khronos\Vulkan\Drivers` location is the older method for
> locating drivers, but is **the primary location for software based drivers**."

It requires admin rights (HKLM) but **no driver signing, no PnP device, no
WHQL**. Note the loader does not read `HKEY_CURRENT_USER` for *drivers* (only
for layers), so per-user install means `VK_DRIVER_FILES`. The commonly-repeated
"RS3+ blocks HKLM" advice applies to PnP graphics drivers in the driver store,
not to standalone software ICDs. SwiftShader registers exactly this way.

Driver policy **LDP_DRIVER_2** further confirms the model: a driver "must not
crash if it detects that there are no supported Vulkan Physical Devices", with
the note that "the loader has no direct knowledge of what devices (**virtual or
physical**) may be supported by a given driver."

### 3.6 Skeletons and Rust prior art

**Best starting skeleton: Khronos's Mock ICD** in Vulkan-Tools (Apache-2.0) — a
generated-from-vk.xml, device-less null driver. Its `.def` file is the exact
export list of a real surface-handling ICD. Generated by
`scripts/generators/mock_icd_generator.py` (1,481 lines) into
`function_declarations.h` (4,244 lines) + `function_definitions.h` (4,887
lines), covering **823 distinct entry points**. So **~9,100 generated lines is
the floor for "an ICD that responds to every entry point"**, before any
marshalling — a useful calibration.

**Rust prior art: Kazan** (<https://github.com/kazan-3d/kazan>, canonical at
salsa.debian.org, **LGPL-2.1-or-later**, dormant since ~2019). The only
substantially complete Rust ICD I could find. Beyond the handle pattern above it
is instructive for: exporting exactly the three symbols with `#[no_mangle] pub
unsafe extern "system"`; negotiating `ICD_VERSION = 5`; a compile-time signature
check `const ASSERT_TYPE_…: api::PFN_vkGetInstanceProcAddr = Some(vk_icdGetInstanceProcAddr);`
that catches ABI drift; and generating its own ICD manifest at build time into
`OUT_DIR` with an absolute `library_path`, which is a clean dev-loop pattern.
**Note the LGPL licence** — study it, do not copy code into a permissive
project.

`google/vk-layer-for-rust` (Apache-2.0, active, built on `ash`) and
`vulkanalia`'s `layer/` example are good Rust references for the *loader
plumbing*, even though we are not building a layer.

**No production Rust Vulkan ICD exists.** We would be first, which is a risk
worth naming.

So: **~70k generated lines for a curated ~50% coverage, ~100–120k per side for
full coverage.** Hand-writing this is not an option, which `api-scale.md`
already concludes.

### 4.2 Rust tooling

| Crate | Approach | Status | Licence |
|---|---|---|---|
| **`vk-parse`** | `xml-rs` → lossless typed AST | **0.21.0, 2026-06-08; actively maintained** (tracks new registry attributes) | **MIT OR Apache-2.0** |
| `ash` | `vk-parse` + `vkxml` + `quote`/`syn` + `nom` + pinned `bindgen` | Repo alive (63 commits in 2026); **crates.io stale at 0.38.0+1.3.281, 2024-04-01** | MIT OR Apache-2.0 |
| `vulkano` | `autogen/` workspace member: `vk-parse` + `nom` + `quote`/`syn`/`prettyplease` | Alive (commits to 2026-07-30) | MIT OR Apache-2.0 |
| `vulkanite` | **`quick-xml` + serde** into typed structs | 0.0.12, 2026-06-15 | MIT OR Apache-2.0 |
| `vulkanalia` | Generator is **Kotlin**, emits Rust as strings | Alive, 0.35.0 (2026-02) | **Apache-2.0 only** |
| `erupt` | `roxmltree` + **`lang-c`** (a real C11 parser) | **Unmaintained** — frozen 2022-11-14; README says use ash | Zlib |
| `vk-sys` | — | **Dead**, archived 2022 | MIT/Apache-2.0 |
| `gfx-hal` | hand-written HAL, no codegen | **Dead**; successor `wgpu-hal` also hand-written | MIT OR Apache-2.0 |

**`vk-parse` is the right parser** and is a trivially light dependency (only
`xml-rs`). Coverage is complete for what we need: `structextends`, `len`,
`altlen`, `optional` (raw string preserved, so `"false,true"` survives),
`externsync`, aliases, `<require>` blocks with `api`/`profile`/`depends`,
spirvcapabilities, videocodecs, plus `stride`, `validstructs` (the pNext
whitelist), `objecttype`, `noautovalidity`, `selector`/`selection`,
`successcodes`/`errorcodes`. Errors are collected rather than fatal, so a new
registry attribute does not abort the parse.

**Its one significant gap: there is no C type model.** Types come out as
`NameWithType { type_name, name, code }` where `code` is **raw C text with
original whitespace**:

```
name=pBuffers type=Some("VkBuffer") code="const VkBuffer* pBuffers"
              len=Some("bindingCount") optional=Some("false,true")
```

`src/c.rs` is a char tokenizer, not a declaration parser. Every downstream
project re-solves pointer-depth/const/array extraction independently — ash with
`nom`, erupt with `lang-c`, vulkanalia by hand in Kotlin, Venus with its own
`VkDecl`. **Budget for writing this.**

**Do not plan to fork ash's generator.** It emits `TokenStream`s directly from
`vk_parse`/`vkxml` with no reusable intermediate model — its only `struct
Command` is declared *inside* a function and its fields are already-rendered
tokens — and, decisively, **it ignores `len`, `altlen`, `optional`,
`externsync` and `stride` entirely for commands** (ash's slice-taking wrappers
are hand-written). Worth stealing: its `nom` C-parameter grammar and its
`<require>`/`<extension>` resolution with provenance tracking.

**Two better models to read:** `vulkanite`'s `generator/src/structs.rs`
(1,079 lines, MIT/Apache-2.0) has a genuinely semantic two-layer type model —
`Type::{Void, VoidPtr, Path, Ptr, DoublePtr, CStrArr, ArrayEnum, ArrayCst,
Bitfield, …}` and `AdvancedType::{Handle, HandlePtr, HandleArray(ty, len_param),
Struct, Enum, Func, CString, …}`. `AdvancedType::HandleArray` is exactly the
distinction a remoting layer needs, and it resolves len↔array pairing into an
explicit map. `vulkanalia`'s model is also better than ash's but collapses
`optional` to a boolean, losing per-indirection information, and is
Apache-2.0-only.

**The highest-leverage discovery here:** Vulkan-Headers now ships
`registry/vulkan_object.py` + `registry/base_generator.py` (Apache-2.0,
© Khronos) which wrap `reg.py` and produce a **typed, fully-resolved dataclass
graph** — `Extension`, `Version`, `Handle`, `Command`, `Param`, `Struct`,
`Member`, `Enum`, `Bitmask`, `FuncPointer`, `ExternSync`, `Format`,
`VideoCodec` — with reverse links and pre-parsed externsync. **Run it once,
serialise to JSON, and write the Rust codegen against a clean typed model
instead of re-parsing XML.** That sidesteps `vk-parse`'s missing C type model
entirely. Licence note: vendoring the scripts inherits Apache-2.0; generating
and shipping only the *output* is unencumbered.

**No Rust crate generates Vulkan serialisation or RPC marshalling from vk.xml.**
That was searched from both directions and does not exist. We would be building
it.

### 4.3 The genuinely hard parts, and how the two prior projects solve them

**pNext chains** — 843 extenders, 147 distinct parents. Two proven and opposite
architectures:

- **Venus: per-parent switch, no length prefix.** For each extendable struct it
  emits `vn_{sizeof,encode,decode}_T_pnext`, which walks the chain, matches
  `sType` against a switch of the structs *that parent* accepts, recurses, and
  re-linearises. `sType`/`pNext` are never sent as payload — the decoder
  re-synthesises `sType` from a compile-time constant. Unknown nodes are
  silently dropped. Runtime `COND_API`/`COND_EXT` guards prevent encoding
  something the negotiated peer cannot decode. Three decode variants: `_pnext`
  (reply path — walks the caller's *existing* chain, matching by sType),
  `_pnext_temp` (request path — allocates from a bump allocator), `_partial`.
- **gfxstream: one global switch plus a length prefix.** `putBe32(currExtSize)`
  per link with 0 terminating; unknown links are skipped and the walk continues
  down `pNext`. Requires a generated `extension_struct_size` switch over every
  `VkStructureType` — 4,266 lines on its own.

Two wrinkles a naive design misses. First, gfxstream threads a **`rootType`**
through every marshal function because **`sType` is not globally unique once you
add private extensions** — `VK_GOOGLE_gfxstream` reuses numeric sTypes that
collide with `VK_EXT_fragment_density_map`, and a mapping table disambiguates by
root. **If we ever define private sTypes, design for this on day one.** Second,
both have a negotiated capability bitmask that can zero a struct's size, i.e.
drop it from the wire — the mechanism that makes version skew survivable.

Universal trap: the decoder cannot allocate a node until it knows the sType, so
**sType must precede the body**. And reply chains are a different problem
entirely, because the caller already owns the chain and you must match rather
than allocate.

**`void*` and unions.** 103 genuine non-`pNext` `void*` members. vk.xml
disambiguates them only via `len` — Venus formalises this as `is_blob()`
(indirection depth 1, base type `void`, has a `len`). Everything else —
`window`, `handle`, `hostAddress`, `pHostPointer`, `pUserData`,
`pCheckpointMarker` — is an opaque pointer that **cannot cross the boundary**
and needs a per-field policy decision. For us `pHostPointer` is especially
interesting, since that is `VK_EXT_external_memory_host` and the arena gives it
a real meaning.

Unions are worse: 16 exist but **only 10 `selector=` annotations exist in the
entire registry**, so most have no machine-readable discriminator. Both projects
punt — Venus hardcodes tags for exactly three unions and refuses to serialise
any struct containing another; gfxstream always marshals member `[0]`. Both are
correct only because the members happen to be same-sized POD.

**`len=` vs `altlen=`.** `len` may be a latexmath equation, another member's
name, `"null-terminated"`, `"1"`, a C99 expression, "or a custom expression that
cannot be used directly by code generation". It is **comma-separated per
indirection level** (`len="usageCountsCount,1"`). There are **only 5 latexmath
cases in the whole registry**, and `altlen` exists precisely to give the
plain-C equivalent. **Read `altlen`; do not build a LaTeX parser.** gfxstream
instead hardcodes the cases by (struct, field) pair, which is the worse choice.

**`optional=`.** 2,552 uses. `optional="false"` alone is not supported but
`"false,true"` is — hence the per-indirection strings. gfxstream also treats
**`noautovalidity`** (378 uses) as implying "needs a null flag", on the
reasoning that complex validity usually means optional in practice. On the
wire, Venus writes a one-word `vn_encode_simple_pointer` boolean; gfxstream
writes an 8-byte **big-endian pointer value as a token** and echoes it back for
cross-checking. **Prefer Venus's — it does not leak addresses and is smaller.**

A warning worth internalising, from gfxstream's own source comment: "Vulkan
updates change certain pointers from non-optional to optional. We want to keep
our encoder/decoder backward compatible." **vk.xml optionality is not stable
across releases.** A wire format pinned directly to vk.xml semantics will
silently break on a header bump. **Version the wire format explicitly** — which
reinforces `api-scale.md`'s decision to pin `vk.xml` through nix.

**Output parameters and the two-call count idiom.** vk.xml has **no `output`
attribute**; you infer it from "non-`const` pointer parameter", which
gfxstream's own source calls "a rough attempt to infer where a type could be an
output". Venus models it as three-state validity, which is the better design:

```
VALID   = 0  # initialized, e.g. an input to the driver
INVALID = 1  # uninitialized, e.g. an output to the driver
PARTIAL = 2  # partially initialized, such as an output to the driver that is also a handle
             # (because the id is specified by the driver) or a struct (because it can
             # potentially include handles, sType, or pNext)
```

hence its `_partial` encode/decode variants. And Venus **clamps array replies
against the caller's buffer**:

```c
if (vn_peek_array_size(dec)) {
    const uint32_t iter_count = vn_decode_array_size(dec, (pPhysicalDeviceCount ? *pPhysicalDeviceCount : 0));
    for (uint32_t i = 0; i < iter_count; i++) vn_decode_VkPhysicalDevice(dec, &pPhysicalDevices[i]);
} else { vn_decode_array_size_unchecked(dec); pPhysicalDevices = NULL; }
```

gfxstream does **not** clamp — it overwrites `*pCount` from the reply before
reading the array. Copy Venus here. Note that under our security model this is
not about defending against a hostile peer; it is that an unclamped write is a
buffer overflow *in our own code* the moment either side has a bug, and the
clamp costs one comparison.

**Handles — the most consequential architectural choice.** Two opposite designs:

- **Venus: app-side-assigned object IDs.** The client picks the id; the GPU side
  keeps an id→object table; generated `vn_replace_T_handle()` walks whole structs
  rewriting embedded handles in place before calling the real driver. **Creation
  needs no round trip**, which is a large latency win over any transport.
- **gfxstream: GPU-side-assigned boxed handles** (§1.3), with
  `delayed_delete_VkDevice(boxed, unboxed, cb)`.

The **delayed-delete machinery is load-bearing and is not derivable from
vk.xml**: you cannot free a GPU-side object the instant the app side says
`vkDestroy*`, because in-flight command buffers may still reference it. Budget
for it explicitly.

My recommendation is **Venus's client-assigned ids for the wire, with
gfxstream's richer per-object table on the GPU side** — the id is what crosses,
the table is what holds dispatch pointers, ordering state and deferred
destruction. The two are complementary rather than exclusive.

**Function pointers — 11 types, and neither project marshals them.** Venus's
`is_serializable()` returns false for funcpointers, so `VkAllocationCallbacks`
is unserialisable; because `pAllocator` is optional the command is still
generated, with `if (pAllocator) assert(false);`. **Venus simply does not
support host allocators**, and Mesa's driver strips `pAllocator` above the
protocol. gfxstream special-cases it into a local copy. Either is fine.

The harder case is **debug callbacks** (`PFN_vkDebugUtilsMessengerCallbackEXT`),
which need a **reverse channel** because the callback must run in the app side's
address space. **Neither project implements a generated reverse-call path** —
Venus does not support debug_utils messengers in the protocol at all; gfxstream
handles them GPU-side-locally. **This is a real usability problem for us**,
because validation layers are the primary debugging tool for an ICD and we will
want their messages on the app side. It is bespoke work outside generated
marshalling and should be planned for early rather than discovered late.

`PFN_vkVoidFunction` is special again: `vkGetInstanceProcAddr` and
`vkGetDeviceProcAddr` must be answered **locally** from a generated dispatch
table and never forwarded (gfxstream's `func_table.cpp` is 4,822 lines for
this).

**`externsync`** appears 416 times and tells us which parameters the application
must externally synchronise — which matters the moment we multiplex several
application threads onto one ring.

### 4.4 Recommended approach

1. **Pin `vk.xml` through nix** (already the plan) and treat the wire format as
   explicitly versioned, independent of the registry version.
2. **Build the type model once**, either by running Khronos's
   `vulkan_object.py`/`base_generator.py` and serialising to JSON, or by
   layering a C-declaration parser over `vk-parse`. The former is less work and
   less risk; the latter keeps the toolchain pure Rust. Given the nix dev shell
   already pins Python-adjacent inputs comfortably, I lean to the former for the
   model and pure Rust for the emitter.
3. **Emit Rust with `quote`/`prettyplease`**, following vulkano's and
   vulkanite's precedent.
4. **Generate the passes gfxstream found necessary** (§1.3): count → reserve →
   marshal on the sending side; unmarshal → deepcopy → transform → handle-map on
   the receiving side. Do not try to collapse them; both mature projects have a
   separate size pass for a reason.
5. **Scope by what Zink needs first** (§5), which is roughly Venus's curated set
   rather than the full registry. ~70k generated lines rather than ~120k, and it
   is the difference between a feasible first milestone and an infeasible one.

A note on the Rust angle: a generator emitting *Rust* from a typed model should
be materially smaller than gfxstream's 14,000 lines of Python emitting C++,
because `quote!` is a better emitter than string concatenation and because
`ash`/`vk-parse` already model much of the registry. I would estimate the
generator at low thousands of lines, but that is an estimate, not a measurement.

## 5. What Zink, DXVK and vkd3d-proton actually demand

This section decides project scope, and the answer is not the one the plan
assumes. **The hourglass does not have a single waist.** Zink is comfortably
achievable; modern DXVK and vkd3d-proton are not, for one specific reason.

Ranked by hostility to a forwarding ICD:
**Zink (viable) ≪ DXVK 3.x (hard) ≈ vkd3d-proton (hard)**.

### 5.1 Zink — achievable, and there is direct precedent

Status confirmed: Mesa's `docs/features.txt` lists zink as DONE for
**GL 4.6 / GLSL 4.60** and **GLES 3.2 / GLSL ES 3.2**, and zink appears on the
Khronos conformant-products list for OpenGL 4.6 (Collabora, on PowerVR):

```
GL_VENDOR: Collabora Ltd | GL_RENDERER: zink (PowerVR D-Series DXTP-16-512 MC1)
GL_VERSION: 4.6 (Core Profile) Mesa 22.3.5 | Display: X11 EGL/GLX
```

- <https://gitlab.freedesktop.org/mesa/mesa/-/raw/main/docs/features.txt>
- <https://www.khronos.org/conformance/adopters/conformant-products/opengl>
- <https://docs.mesa3d.org/drivers/zink.html>

Zink+NVK is the default GL driver for NVIDIA on Mesa ≥ 25.1. (I could not
confirm a zink entry on the OpenGL **ES** conformant-products list.)

**Hard requirements.** Only five extensions carry `required=True` in
`src/gallium/drivers/zink/zink_device_info.py`, whose header comment defines
the semantics — "the generated code debug_prints `ZINK: {name} required!` and
returns NULL if the extension is unavailable":

| Extension | Core in |
|---|---|
| `VK_KHR_maintenance1` | 1.1 |
| `VK_KHR_maintenance5` | 1.4 |
| `VK_KHR_create_renderpass2` | 1.2 |
| `VK_KHR_dynamic_rendering` | 1.3 |
| `VK_KHR_descriptor_update_template` | 1.1 |

Plus one hard runtime bail-out in `zink_screen.c`:

```c
if (!screen->info.have_KHR_timeline_semaphore && !screen->info.feats12.timelineSemaphore) {
   mesa_loge("zink: KHR_timeline_semaphore is required");
   goto fail;
}
```

`check_base_requirements()` warns but does *not* fail on `logicOp`,
`scalarBlockLayout`, `VK_KHR_maintenance1`, `VK_EXT_custom_border_color`,
`VK_EXT_line_rasterization` — "WARNING: Some incorrect rendering might occur".

**The authoritative full set is the machine-readable profile**
`src/gallium/drivers/zink/VP_ZINK_requirements.json`, which is what
`zink_check_requirements` validates against. Note it **contradicts the prose**:
`zink.rst` says "Vulkan 1.0" for the GL 2.1 baseline, but the profile sets
`VP_ZINK_gl21_baseline` at `api-version: 1.2.0` and the GL4.3+ profiles at
`1.3.0`. **Treat the JSON as authoritative.** The GL 2.1 baseline additionally
requires `VK_KHR_imageless_framebuffer`, `VK_EXT_custom_border_color` (with
`customBorderColorWithoutFormat`), `VK_EXT_provoking_vertex`,
`VK_EXT_line_rasterization` (all six line-mode features),
`VK_KHR_swapchain_mutable_format`, `VK_EXT_border_color_swizzle`,
`VK_KHR_incremental_present`, `scalarBlockLayout`, and the core features
`logicOp`, `fillModeNonSolid`, `alphaToOne`, `shaderClipDistance`.

The ladder to GL 4.6, delta by level:

| GL | Adds |
|---|---|
| 3.0 | `independentBlend`; **`VK_EXT_transform_feedback`**, `VK_EXT_conditional_rendering`; `D32_SFLOAT_S8_UINT` DS-attachment |
| 3.1 | `maxPerStageDescriptorSamplers ≥ 16` |
| 3.2 | `depthClamp`, `geometryShader`, `shaderTessellationAndGeometryPointSize`; `VK_EXT_depth_clip_enable` |
| 3.3 | `dualSrcBlend`; `VK_EXT_vertex_attribute_divisor` |
| 4.0 | `sampleRateShading`, `tessellationShader`, `imageCubeArray`; `VK_KHR_maintenance2` |
| 4.1 | `multiViewport`; 16384 2D / 2048 3D limits, `maxViewports ≥ 16` |
| 4.2 | `VK_EXT_image_2d_view_of_3d`; storage-image extended formats; `shaderDrawParameters` |
| 4.3 | `robustBufferAccess`; sampled-image format list |
| 4.4 | `B10G11R11_UFLOAT` as vertex format; `samplerMirrorClampToEdge` |
| 4.5 | `shaderCullDistance` |
| 4.6 | `samplerAnisotropy`, `depthBiasClamp`; `VK_KHR_draw_indirect_count` |

So **baseline Vulkan 1.0 with no extensions gets you nothing** — zink will not
initialise. But everything on that list is ordinary core-ish functionality that
a forwarder passes straight through.

**The crucial negatives for us:**

- **`VK_KHR_buffer_device_address` is optional** — a plain entry in
  `zink_device_info.py` with no `required=True`.
- **`VK_EXT_descriptor_buffer` is optional** — `gl46_optional`, opt-in via
  `ZINK_DESCRIPTORS=db`; the default `auto` uses classic descriptor sets.
- **`VK_EXT_descriptor_indexing` is optional** — it gates
  `GL_ARB_bindless_texture` only.
- **dma-buf / external memory are optional** — `VK_KHR_external_memory` is
  needed only "to support the DRI code-path"; the Kopper WSI path needs only
  `VK_KHR_swapchain`. In `zink_screen.c` the dmabuf pipe cap is gated on
  `have_KHR_external_memory_fd && have_EXT_external_memory_dma_buf`; without
  them you lose GBM/DRI3 buffer sharing and GL-CL interop, not GL itself.
- `VK_EXT_extended_dynamic_state*` and `VK_EXT_graphics_pipeline_library` are
  in the `gl46_optimal` **performance** tier, not the correctness tier.

**And the single best piece of evidence in this document: Mesa's own CI runs
zink on top of Venus.** From `src/gallium/drivers/zink/ci/gitlab-ci.yml`:

```yaml
zink-lavapipe:            DEQP_SUITE: zink-lavapipe   VK_DRIVER: lvp
zink-venus-lavapipe:      DEQP_SUITE: zink-venus-lavapipe
zink-venus-lavapipe-full: ...
```

That is GL-on-Vulkan running on a *forwarded* Vulkan across a virtio-gpu
boundary, on a CPU backend, gated in upstream CI. Our GL story has precedent
and a reference configuration to compare against. `zink_screen.c` also has
explicit CPU-device selection logic, so zink-on-software-Vulkan is a
first-class configuration.

The one unavoidable cost: zink uses persistently mapped
`HOST_VISIBLE|HOST_COHERENT` memory for `GL_ARB_buffer_storage`
(`PIPE_MAP_PERSISTENT` handling in `zink_resource.c`; `alloc_info->flags |=
VK_MEMORY_PROPERTY_HOST_COHERENT_BIT` for `MAP_COHERENT`/`PIPE_USAGE_DYNAMIC`),
mandatory from GL 4.4. The arena handles this natively — which is exactly why
the arena is the right requirement.

### 5.2 DXVK — bimodal, and the modern branch is hostile

The "DXVK 2.x" framing is out of date: the current series is **3.0.x**, and the
decisive change landed in **2.7**.

`src/dxvk/dxvk_instance.h`:

```cpp
constexpr uint32_t DxvkVulkanApiVersion = VK_API_VERSION_1_3;
```

enforced twice in `dxvk_device_info.cpp`. In practice you need a Vulkan
**1.4**-class feature set, because `maintenance5` and `maintenance6` are
hard-required and both are 1.4 core. The wiki says so outright — "For DXVK
3.x … A compatible driver should support Vulkan 1.4"
(<https://github.com/doitsujin/dxvk/wiki/Driver-support>), quoting minimum
drivers RADV 25.0, NVIDIA 575.51.02, NVK 25.1, ANV 25.1.

Required device extensions in 3.x (`getFeatureList()`, `require=true`):
`VK_EXT_depth_clip_enable`, `VK_EXT_robustness2` (`robustBufferAccess2` **and**
`nullDescriptor`), `VK_KHR_load_store_op_none`, `VK_KHR_maintenance5`,
`VK_KHR_maintenance6`, `VK_KHR_swapchain`. Required 1.2 features include
`descriptorIndexing`, `runtimeDescriptorArray`,
`descriptorBindingPartiallyBound`, `timelineSemaphore`, `scalarBlockLayout`,
`vulkanMemoryModel`, `hostQueryReset`, `samplerMirrorClampToEdge`, `shaderInt8`
— and, fatally, **`bufferDeviceAddress`**.

A limit not to under-advertise: **`maxPushConstantsSize ≥ 256`**
(`MaxTotalPushDataSize` in `dxvk_limits.h`), unless you expose
`VK_EXT_descriptor_heap`.

**The killer.** DXVK 3.x compiles shaders with the `dxbc-spirv` backend, which
emits unconditionally, for every shader (`dxbc-spirv/spirv/spirv_builder.cpp`):

```cpp
enableCapability(spv::CapabilityPhysicalStorageBufferAddresses);
enableCapability(spv::CapabilityVulkanMemoryModel);
pushOp(m_memoryModel, spv::OpMemoryModel,
  spv::AddressingModelPhysicalStorageBuffer64,
  spv::MemoryModelVulkan);
```

and binds UBOs/SSBOs as raw 64-bit addresses through push constants —
`dxvk_pipelayout.h` returns `sizeof(VkDeviceAddress)` for uniform/storage
buffer block entries, and `dxvk_context.cpp` fills them from
`slice.getSliceInfo().gpuAddress`. This is the pipeline layout model, not an
optional fast path.

By contrast **DXVK ≤ 2.6.x had only two required device extensions**
(`VK_EXT_robustness2`, `VK_KHR_swapchain`) and enabled `bufferDeviceAddress`
only opportunistically for NVX CUDA interop, with the source comment
"VK_KHR_buffer_device_address is expensive on some drivers".

So **DXVK ≤ 2.6.x is a realistic target; DXVK ≥ 2.7 is not**, absent VA
identity.

Secondary trap: `VK_EXT_transform_feedback` is *optional* to DXVK, but without
it `CreateGeometryShaderWithStreamOutput` returns `DXGI_ERROR_INVALID_CALL`
(`d3d11_device.cpp`) while the device still advertises FL 11_0+. Any title
using stream output hard-fails rather than degrading. The D3D feature-level
ladder otherwise depends on `tessellationShader`/`multiDrawIndirect`/
`drawIndirectFirstInstance` (else capped at 10_1), `logicOp`/
`vertexPipelineStoresAndAtomics` (else 11_0), tiled resources tier 2 +
typed-UAV-load formats (else 11_1), conservative raster + ROVs (else 12_0).

### 5.3 vkd3d-proton — out of scope, structurally

`include/vkd3d.h`: `#define VKD3D_MIN_API_VERSION VK_API_VERSION_1_3`.

Hard-enforced in `libs/vkd3d/device.c`, each aborting device creation:
`samplerMirrorClampToEdge`; `robustBufferAccess2` + `robustImageAccess2` +
`nullDescriptor`; `shaderDrawParameters`; `VK_KHR_push_descriptor`; and
`maintenance5` + `maintenance6` — the last two being 1.4 core and **not
documented in the README**. Plus a descriptor-indexing floor of **1,000,000**
update-after-bind sampled images / storage images / storage buffers per stage
and 2,048 samplers (`VKD3D_MIN_VIEW_DESCRIPTOR_COUNT`, `vkd3d_private.h`).

Encouragingly much is optional: `VK_EXT_descriptor_buffer`,
`VK_EXT_mutable_descriptor_type`, all ray tracing (`NO_DXR` disables it
cleanly), and sparse/tiled resources (costing only `TiledResourcesTier`).

But buffer device address is not optional and cannot be made so, because
**the D3D12 API itself exposes `ID3D12Resource::GetGPUVirtualAddress()` to the
application**. Every buffer gets the usage bit unconditionally
(`libs/vkd3d/resource.c`):

```c
buffer_info.usage |= VK_BUFFER_USAGE_SHADER_DEVICE_ADDRESS_BIT;
```

There is an entire VA reverse-lookup subsystem (`libs/vkd3d/va_map.c`) mapping
an application-supplied VA back to a resource, and vkd3d writes VAs into a
host-visible GPU buffer (`raw_va_aux_buffer`, bound via
`VKD3D_BINDLESS_SET_EXTRA_RAW_VA_AUX_BUFFER`) that shaders read and then
dereference — writes a proxy never observes. dxil-spirv turns on
`AddressingModelPhysicalStorageBuffer64` whenever root descriptors exist, i.e.
essentially always, and unconditionally for ray tracing.

**Verdict: vkd3d-proton cannot be supported by a forwarder that does not make
GPU-side virtual addresses meaningful on the app side.** That is a property of
the D3D12 contract, not a matter of effort.

### 5.4 Consolidated table

| Proxy-hostile feature | Zink | DXVK ≤2.6 | DXVK ≥2.7/3.x | vkd3d-proton |
|---|---|---|---|---|
| `bufferDeviceAddress` / raw VAs in app data | No (optional) | No (NVX only) | **Required** | **Structural** |
| Shaders using `PhysicalStorageBuffer64` | No | No | **Unconditional** | **Effectively always** |
| Persistently mapped `HOST_VISIBLE\|HOST_COHERENT` | **Yes** (GL 4.4) | Yes | Yes | Yes |
| `VK_EXT_descriptor_buffer` / `_heap` | Optional | n/a | Optional | Optional |
| External memory / dma-buf | Optional | Optional | Optional | Optional |
| Timeline semaphores + host waits | **Required** | Required | Required | Required |
| Sparse / tiled resources | Optional | Optional (costs FL) | Optional (costs FL) | Optional (costs tier) |
| Ray tracing | n/a | n/a | n/a | Optional |
| Minimum Vulkan | 1.2 / 1.3 | 1.3 | 1.3 code, **1.4 real** | 1.3 code, **1.4 real** |

Note that with the arena, the "persistently mapped coherent memory" row — which
would be the killer for a copying design — costs us nothing. The rows that
remain fatal are the buffer-device-address ones, and the arena does not help
with those, because the problem is not *where* the memory is but that the
application holds a 64-bit address in the GPU side's address space.

### 5.5 What this does to the plan

The stated goal — "Vulkan is the single waist of the hourglass, and we get GL
via Zink and D3D via DXVK/vkd3d for free" — holds for **GL via Zink** and for
**D3D9/10/11 via DXVK ≤ 2.6**. It does **not** hold for D3D12 via
vkd3d-proton, nor for current DXVK.

Three coherent positions, and this is a scoping decision to take now:

1. **Zink first.** Ship GL; treat DXVK ≤ 2.6 as a stretch. Lowest risk, real
   utility, and Mesa CI already proves the configuration.
2. **Commit to VA identity.** Vulkan provides *some* machinery —
   `VkBufferOpaqueCaptureAddressCreateInfo` and
   `VkMemoryOpaqueCaptureAddressAllocateInfo` (both core 1.2, used by capture
   tools like RenderDoc for exactly this replay problem).

   **Correction to an earlier draft of this document:** I had suggested pairing
   these with `VK_MEMORY_MAP_PLACED_BIT_EXT` to put the arena at the same host
   virtual address on both sides. That combination is **explicitly forbidden**.
   `VUID-VkMemoryMapInfo-flags-09575` states that if `VK_MEMORY_MAP_PLACED_BIT_EXT`
   is set, the memory object "**must not** have been imported from a handle type
   of `HOST_ALLOCATION_BIT_EXT` or `HOST_MAPPED_FOREIGN_MEMORY_BIT_EXT`", with
   the same rule for `VK_MEMORY_UNMAP_RESERVE_BIT_EXT`
   (`-09580`). Arena-backed memory is imported from precisely those handle
   types, so placed mapping and the arena are mutually exclusive by
   specification. `VK_EXT_map_memory_placed` is otherwise well supported (ANV
   and RADV both expose it at page-size alignment) — it simply cannot be used
   here.

   That removes the mechanism I thought made this tractable. VA identity would
   have to be achieved by ordinary means — reserving matching address ranges
   with `mmap(MAP_FIXED)` / `VirtualAlloc(MEM_RESERVE)` before either side
   allocates, and hoping the GPU-side driver's own VA assignment can be steered
   by capture-replay addresses. That is a research effort with a materially
   worse prognosis than I gave it above.
3. **Accept D3D12 is out of scope** and run D3D12 applications inside the guest
   next to the GPU.

I recommend (1), with (3) as the honest answer for D3D12 today, and (2)
revisited only once Zink works.

## 6. Transport options on this machine

Measured and source-verified. Note this section concerns the **control plane and
the fallback data plane** — if the arena works, bulk data does not travel over
a transport at all, which is the entire point.

### 6.1 Summary

| Transport | Shared mapping? | Bandwidth | Latency | Windows driver, Secure Boot | Verdict |
|---|---|---|---|---|---|
| **ivshmem-plain** | **Yes, true zero-copy** | ~3 GB/s per channel, ~12.5 GiB/s aggregate | sub-µs polled | ✅ LG installer, MS WHCP | **Arena + rings** |
| **ivshmem-doorbell** | Yes, but memory owned by `ivshmem-server` | same | **8.1 µs** RT with MSI-X | ✅ same driver | Signalling, if server-owned memory is acceptable |
| **virtio-serial** | No, 4 copies each way | few MB/s | ms-class | ✅ `vioser` | **Control plane only** |
| **vsock** | No | 22–25 Gbps; 234–270 Gbps with `MSG_ZEROCOPY` on Linux | tens of µs | ✅ `viosock`, STREAM only | **Best socket abstraction; cross-machine ready** |
| **TCP / virtio-net** | No | ~22.6 Gbps single stream | ~35 µs RTT | ✅ `netkvm` | Fallback / cross-machine |
| **vhost-user** | Host gets *guest* memory | — | — | — | Wrong direction |
| **virtio-gpu blob / hostmem BAR** | Guest gets *host* memory | — | — | ❌ no Windows guest driver | Right idea, wrong direction, no driver |
| **pvrdma / RDMA** | — | — | — | — | **Removed in QEMU 9.1** |

### 6.2 virtio-serial — control plane only, and worse than expected

Guest: Linux `/dev/vport0p1` + `/dev/virtio-ports/<name>`; Windows `vioser.sys`
opened as `CreateFile("\\\\.\\Global\\<port name>")` (the driver creates the
symlink in `vioserial/sys/Port.c`). WHCP-signed.

**No published throughput benchmark exists** — I searched and so did a dedicated
stream. But the code-level ceiling is damning:

| Constraint | Value | Source |
|---|---|---|
| Guest→host write chunk | 32 KiB max | `virtio_console.c:817` |
| Host→guest RX buffer | exactly PAGE_SIZE (4096) | `virtio_console.c:1298` |
| Virtqueue depth | 128 | `virtio-serial-bus.c:1036` |
| QEMU chardev read buffer | `CHR_READ_BUF_LEN 4096` | `include/chardev/char.h:37` |
| Host→guest per-iteration cap | 4096 | `virtio-serial-bus.c:321` |

QEMU moves **at most 4 KiB host→guest per main-loop wakeup, with a guest
interrupt per 4 KiB**, and there is **no iothread support** (`grep -c iothread`
on both files = 0) — it all runs under the BQL. Four copies each direction, and
host→guest is far worse than guest→host. The KVM wiki's own design intent: "For
relatively low rate of data transfer -- a few MB/s"
(<https://www.linux-kvm.org/page/VMchannel_Requirements>).

**Use it for handshake, capability negotiation and out-of-band control. Never
for data.** It is already attached to this VM, which makes it the natural
bootstrap channel.

### 6.3 vsock — the right abstraction boundary

`-device vhost-vsock-pci,guest-cid=3`. CIDs: 0 hypervisor, 1 loopback, 2 host.

**Windows works, with caveats.** `AF_VSOCK` is **not a fixed constant** — the
driver is assigned an address family at install time and must be queried at
runtime:

```c
#define VIOSOCK_NAME L"\\??\\Viosock"
#define IOCTL_GET_AF 0x0801300C
__inline ADDRESS_FAMILY ViosockGetAF();
```

Then ordinary Winsock. **`SOCK_STREAM` only** — `viosock/lib/install.c`
registers exactly one provider ("Virtio Vsock STREAM"); no DGRAM, no SEQPACKET.
Still young: an open BSOD-after-migration bug
(<https://github.com/virtio-win/kvm-guest-drivers-windows/issues/1485>),
CVE-2026-46655 fixed in #1568, and
<https://github.com/virtio-win/kvm-guest-drivers-windows/issues/1476> suggests
`virtio-win-guest-tools.exe` may not auto-install it — expect a manual Device
Manager install.

Throughput (Garzarella, netdev 2019,
<https://www.spinics.net/lists/netdev/msg561709.html>), Gbps host→guest /
guest→host after optimisation: 4K packets 5.6 / 4.4; 64K 22.9 / 25.0; 512K
25.1 / 25.4. With `MSG_ZEROCOPY` (landed in Linux **6.7**, not 6.4) at 1 MB
buffers: G2H 27 → **270** Gbps, H2G 38 → **234** Gbps
(<https://www.spinics.net/lists/kernel/msg4777142.html>) — sender-side only.

**Shared memory: definitively no.** Three virtqueues (rx/tx/event),
credit-based flow control, and `drivers/vhost/vsock.c` uses
`copy_to_iter()`/`copy_from_iter()` against guest iovecs. The two sides never
map the same pages.

**Why it is still the right abstraction:** it is socket-shaped, so the same
code becomes TCP for the cross-machine case with no protocol change, and it has
a signed Windows driver. Make it the second transport implementation from day
one.

### 6.4 vhost-user, virtio-gpu blob, rutabaga — the direction problem

`vhost-user` passes *guest* memory regions to a host backend over `SCM_RIGHTS`
(`VHOST_USER_SET_MEM_TABLE`), requiring a shareable backend — QEMU errors with
"consider using -object memory-backend-file share=on". We already satisfy that.
But it is the wrong direction: it gives a **host** process access to **guest**
memory, and we need the guest process to reach a shared region.

The reverse now exists as a first-class virtio feature (see §2.2 lead 4), but
`VHOST_USER_BACKEND_SHMEM_MAP` is QEMU 11.1 and this machine runs 10.2.2.

virtio-gpu's host-visible window is `VIRTIO_GPU_SHM_ID_HOST_VISIBLE = 1`,
exposed as **PCI BAR 4** via
`virtio_pci_add_shm_cap(vpci_dev, 4, 0, g->conf.hostmem, ...)`; `hostmem=` both
sizes and enables it. `RESOURCE_MAP_BLOB` maps a host blob into a guest-chosen
offset, and `map_info` returns the required caching
(`CACHE_NONE/CACHED/UNCACHED/WC`) which the guest applies with
`pgprot_writecombine`/`pgprot_noncached`. **All of it assumes host-owns-GPU**,
virglrenderer links into the host VMM, and virtio device/driver roles are not
swappable — a virtio device cannot live in the guest with the driver on the
host. There is no "reverse virtio-gpu" anywhere in QEMU, crosvm, virglrenderer
or the kernel. What *is* reusable is the transport primitive — host-allocated
buffer + guest DMA + signalling — which is exactly ivshmem.

**`vhost-user-gpu` is a dead end**: grepping `hw/display/vhost-user-gpu.c` for
`hostmem`, `blob`, `shm` gives **zero** matches. No host-visible window, so no
Venus and no native contexts — display scanout sharing only.

**`virtio-gpu-rutabaga-pci`**, though present on this machine, needs a guest
driver speaking the gfxstream capset, which exists only in Mesa on Linux.
virtio-win's only GPU driver is `viogpudo`, a basic display driver. So the
packaged gfxstream stack is not directly usable here.

### 6.5 TCP over virtio-net, and RDMA

`-netdev tap,vhost=on` — vhost is **off by default** in raw QEMU
(`net/tap.c`); libvirt turns it on. Host↔guest single stream ~**22.6 Gbit/s**
with vhost-net, ~19.2 without; latency 28,822 TCP_RR trans/s ≈ **34.7 µs RTT**
(<https://www.redhat.com/en/blog/hands-vhost-net-do-or-do-not-there-no-try>).
Costs a full core for the vhost thread.

Multiqueue (`queues=N`, `vectors=2N+2`) helps aggregate load but **a single TCP
stream is pinned to one queue pair and will not scale**. Leave TSO/GSO on;
large MTU matters less than expected because the guest already emits 64 KB
super-packets. Do **not** enable `experimental_zcopytx` — upstream disabled it
by default in 5.3 for head-of-line blocking (commit `098eadce3c62`).
Windows/NetKVM is materially worse than Linux
(<https://github.com/virtio-win/kvm-guest-drivers-windows/issues/167>: Linux
guest >95% of 100G line rate vs Windows Server 2012R2 at 50–60%); the big
Windows win is **RSC**, documented as 7 → 35 Gbps host-to-guest via TAP.

**RDMA is closed.** QEMU's `pvrdma` and the entire RDMA subsystem were
**removed in 9.1** (deprecated in 8.2: "in a bad shape and without active
maintenance"). SoftRoCE over virtio-net is far worse than plain TCP — measured
iperf TCP 19.2 Gbit/s vs `ib_send_bw` ~310 MB/s, because rxe burns CPU on
mandatory software ICRC.

### 6.6 A constraint on the display path specific to this machine

Looking Glass's FAQ states that the Linux client "still needs an EGL-capable
host graphics driver. Direct DMA-BUF import depends on the host GPU and driver;
the client falls back to a copy when it is unavailable."

**This host has no GPU at all.** So an LG-style client here runs on llvmpipe and
takes the slow copy path. Both of the things that make Looking Glass fast are
unavailable. Worth measuring before designing around it — it may well be that
the physical monitor should simply stay attached to the passed-through iGPU,
with the Linux side acting as a headless compute/client node and the display
problem largely disappearing.

For reference, LG's memory sizing formula is
`BASE = ceil(WIDTH*4/256)*256 * HEIGHT * 3`, rounded up to a power of two:
1080p → 64 MiB, 1440p → 128 MiB, 4K → 256 MiB, 8K → 512 MiB.

## 7. Recommended architecture

### 7.1 Shape

```
  APP SIDE (Linux host, no GPU)                 GPU SIDE (Windows VM, Raptor Lake iGPU)
  ┌──────────────────────────────┐              ┌──────────────────────────────────────┐
  │ application                  │              │ shared_vulkan server                 │
  │   ↕ Vulkan loader            │              │   ↕ ash (real ICD dispatch)          │
  │ shared_vulkan ICD (cdylib)   │              │ Intel Vulkan driver → iGPU           │
  │  • generated encoder         │              │  • generated decoder                 │
  │  • handle ids                │              │  • object table (dispatch, ordering, │
  │  • arena suballocator        │              │    deferred destroy)                 │
  └────────┬────────────┬────────┘              └────────┬───────────────────┬─────────┘
           │            │                                │                   │
   ┌───────▼────────────▼────────────────────────────────▼───────────────────▼───────┐
   │  CONTROL REGION            │             PASSTHROUGH ARENA                       │
   │  per-queue SPSC rings,     │  VkDeviceMemory carved from here.                   │
   │  reply slots, timeline     │  Mapped app-side (vkMapMemory returns into it),     │
   │  counters, status/liveness │  imported GPU-side via VK_EXT_external_memory_host. │
   │  words, generation counter │  Command stream carries OFFSETS, never payloads.    │
   └────────────────────────────┴─────────────────────────────────────────────────────┘
              shared memory (mechanism per §2.2), + virtio-serial for bootstrap
```

### 7.2 The decisions, with reasons

**Entry point.** A Vulkan **ICD**, not a layer (§3.1 — a layer cannot exist
without a driver beneath it, and this machine has none). Target loader/driver
interface **7**, degrade to 5. Install to `/usr/share/vulkan/icd.d/` on Linux
and `HKLM\SOFTWARE\Khronos\Vulkan\Drivers` (DWORD 0) on Windows, the latter
being explicitly documented as the primary location for software drivers.
`VK_EXT_headless_surface` rather than remoting a window-system surface.

**Wire format.** Adopt **Venus's `VK_EXT_command_serialization`** (MIT) rather
than inventing one. It is a 134-line specification, direction-neutral, already
generated by 3,126 lines of Python we may reuse or reimplement, and it is
missing only the things that genuinely cannot be serialised. Take Venus's
choices on optional pointers (a one-word boolean, not a leaked address),
`_partial` output handling, and clamping array replies. Take gfxstream's choices
on the pNext encoding (length-prefixed links, 0 terminator) because it survives
version skew better, and on the `rootType` threading if we ever mint private
`sType` values.

**Handles.** Venus's **app-side-assigned object ids on the wire** — creation
needs no round trip, which is the single biggest latency win available — with
gfxstream's **richer per-object table on the GPU side** holding the driver
handle, the dispatch pointer, ordering state and deferred-destroy state. In
Rust that is a `SlotMap`. The two designs are complementary, not exclusive.

**Ring.** Copy the Venus/ASG design, which both projects arrived at
independently: a single-producer/single-consumer circular buffer in the control
region with `head`/`tail`/`status` words and explicit acquire/release atomics;
the consumer **spins while work is arriving** and only sleeps after an
`idleTimeout` with an empty ring, setting an `IDLE` status bit that tells the
producer a notification is needed. **Per queue, and modest in size** — because
the arena carries the data, a ring never has to absorb a texture upload, which
is exactly the mistake `requirements-shared-memory.md` identifies in sharedgl's
single global `SUBMIT` int.

**Command buffers.** Do not send `vkCmd*` individually. Record into a staging
buffer in the arena and ship the whole blob at `vkEndCommandBuffer`/submit time,
decoded by a separate restricted decoder — gfxstream's
`vkQueueFlushCommandsGOOGLE` / `vk_sub_decoder.cpp` pattern, and Venus's
`vkExecuteCommandStreamsMESA`. With the arena this is genuinely zero-copy from
record to execute.

**`vkQueueSubmit` must be asynchronous.** Non-negotiable; encode and return.

**Memory.** The arena, per §2. Pursue **guest-RAM-via-AWE** first if it yields
real guest PFNs, because it needs no device and no driver at all; otherwise
**ivshmem-plain with the Looking Glass Microsoft-signed driver**, mapped
explicitly write-back or write-combining rather than accepting the uncached
default. Advertise the memory-type table of §2.4 so applications choose the
fast path unprompted. Suballocate with a real allocator and generate the
`(memory, offset)` rewrite pass — this is not optional.

**Synchronisation.** Everything is a monotonic 64-bit timeline. Semaphores used
only between GPU-side queues never cross. Fence and timeline counters are
mirrored into the control region so app-side polling is a local load.

**Transport.** Two planes, abstracted from day one:
- **Hot path:** the shared region with a polled ring. Sub-microsecond.
- **Cold path:** a socket for handshake, capability negotiation, wakeups and
  teardown. Use **virtio-serial** initially because it is already attached to
  this VM and needs nothing new; move to **vsock** (signed `viosock` driver
  present) once it is worth the install, because vsock is socket-shaped and
  becomes TCP unchanged for the eventual cross-machine case.

This split also neatly sidesteps the ivshmem plain-vs-doorbell exclusivity
(§2.2): we keep our own memory backend *and* get an out-of-band wakeup channel,
without needing `ivshmem-server` to own the arena.

**Presentation is outside the protocol** (§2.8), exactly as gfxstream does it.
Implement `VK_KHR_swapchain` app-side over GPU-side images, and on present do a
GPU-side copy into a linear arena buffer. But **measure the display path on a
GPU-less client before investing in it** — §6.6 suggests the honest answer may
be to leave the physical panel attached to the passed-through iGPU.

### 7.3 Suggested order of work

1. **Settle the memory mechanism.** Run `vulkaninfo` in the guest for
   `VK_EXT_external_memory_host` and `minImportedHostPointerAlignment`; write
   the ten-line `vkGetMemoryHostPointerPropertiesEXT` probe against both an
   ordinary allocation and the candidate arena; test the AWE PFN question. This
   gates everything and costs a day.
2. **Measure raw shared-memory bandwidth** at each cache mode, and confirm the
   effective memory type under this machine's VFIO configuration.
3. **Build the type model and the generator skeleton**, emitting for a
   deliberately tiny command subset — enough for `vkCreateInstance`,
   `vkEnumeratePhysicalDevices`, `vkCreateDevice`, `vkAllocateMemory`,
   `vkMapMemory`. Prove the round trip end to end before scaling coverage.
4. **Get the ICD loading and enumerating a device** on both OSes, with the
   dispatch-magic contract correct — this is the classic silent-segfault trap.
5. **Widen coverage to Zink's requirement set** (§5.1), and run
   `zink-lavapipe`'s deqp suite against it. Mesa's `zink-venus-lavapipe` CI job
   is a directly comparable reference configuration.
6. Only then consider DXVK ≤ 2.6.

## 8. Risks

Per `security-model.md` these are documented, not designed away. R1–R8 are
maintained in that file; the following are additions and refinements arising
from this research, numbered onward.

### R9 — `VK_EXT_external_memory_host` may not accept our arena
The entire zero-copy design rests on the GPU-side driver importing arena pages
as `VkDeviceMemory`. `vkGetMemoryHostPointerPropertiesEXT` may return
`memoryTypeBits == 0`, which is a *legal* driver response, and is more likely
for a PCI BAR mapping than for ordinary RAM. There are also field reports of
`VK_ERROR_OUT_OF_DEVICE_MEMORY` from this path on some drivers.
*Mitigation:* test before designing further (§7.3 step 1). If it fails, the
fallbacks in §2.1 are all worse and one of them — the copying mode of §2.6 —
does not satisfy the requirement at all.

### R10 — Cache attribute mismatch corrupts silently
Mapping the same physical pages with different cache attributes from two page
tables is architecturally undefined on x86. Because the arena is mapped by both
sides, and because the correct attribute differs per memory type (WC for upload,
WB for readback, §2.3), it is entirely possible to end up with an aliasing
mismatch. The failure mode is silent data corruption under load, not a fault.
*Mitigation:* make the cache attribute a property of the arena sub-region,
agreed at allocation time and identical on both sides; never let one side pick
independently. Treat any need for `honor-guest-pat=on` as a signal we have got
the negotiation wrong.

### R11 — The arena is a fixed-size, pre-negotiated window
Unlike a real Vulkan implementation, we cannot grow host-visible memory on
demand. Every host-visible allocation comes out of a window sized at startup, so
an application that allocates more than we reserved gets
`VK_ERROR_OUT_OF_DEVICE_MEMORY` at an arbitrary point. gfxstream hit this and
answered with a 16 MiB block granularity, 1 MiB rounding and a `u_mm`
suballocator; we inherit the same constraint.
*Mitigation:* size generously, report the real size in the heap so applications
budget against it, and consider growing by adding further regions rather than
resizing.

### R12 — `bufferDeviceAddress` puts DXVK ≥ 2.7 and vkd3d-proton out of reach
Documented at length in §5. Not a bug to fix; a property of those projects and
of the D3D12 contract.
*Mitigation:* scope to Zink and DXVK ≤ 2.6. Revisit VA identity later, if ever.

### R13 — Version skew between the two sides corrupts rather than fails
The Venus wire format encodes command length *implicitly* in the command type:
"It is impossible to skip an unrecognized command type during
deserialization." Two builds generated from different `vk.xml` revisions will
therefore desynchronise the stream and misinterpret every subsequent byte,
rather than reporting a mismatch. Compounding it, gfxstream's own source notes
that **vk.xml's `optional=` semantics are not stable across header releases**,
so "same registry version" is not even sufficient — the *generator* version
matters too.
*Mitigation:* an explicit wire-format version plus a hash of the generated
protocol, exchanged in the handshake before any command is sent, with a hard
refusal on mismatch. Pinning `vk.xml` through nix (R8) is necessary but not
sufficient on its own.

### R14 — No reverse channel means no validation-layer output on the app side
Debug callbacks (`PFN_vkDebugUtilsMessengerCallbackEXT`) must run in the app
side's address space, and **neither Venus nor gfxstream implements a generated
reverse-call path** — Venus does not support debug_utils messengers in its
protocol at all. Validation layers are the primary debugging tool for an ICD, so
this is a real development-velocity risk rather than a niche gap.
*Mitigation:* plan a small bespoke reverse-call channel early — it can be a
simple reply-slot mechanism in the control region — rather than discovering the
need at the point where debugging becomes hard.

### R15 — The Windows GPU-side process must survive without the driver's usual context
Nothing in this design has been validated against a Windows Vulkan driver
running headless in a service or background process, imported-memory-only, with
no swapchain. Intel's Windows driver is not a target its vendor tests this way.
*Mitigation:* none available in advance; discover early by running a trivial
compute workload through the GPU-side server before building on it.

### R16 — Loader unknown-extension trampoline ceiling
`MAX_NUM_UNKNOWN_EXTS` is 250 in the loader. Because we mirror whatever the
remote device exposes, and the loader's known-extension list depends on the
*loader's* header version, an older loader on the app side could run out of
trampolines.
*Mitigation:* filter the advertised extension list to what we actually support
(which we must do anyway for §5), rather than mirroring everything.

### R17 — We would be the first production Rust Vulkan ICD
The only substantially complete prior attempt (Kazan) is dormant since 2019 and
LGPL. There is no well-trodden path, and the dispatch-magic contract in
particular is a place where Rust's natural idioms (`Arc`, trait objects,
`#[repr(Rust)]`) are all wrong in ways the loader only checks in debug builds.
*Mitigation:* copy the `#[repr(C)] { loader_dispatch_ptr: usize, value: T }`
pattern exactly, and add a compile-time signature assertion against the `PFN_*`
typedefs as Kazan does.

### R18 — GPU hangs are visible to a person sitting at the laptop
This sharpens R1 rather than adding to it, and is worth restating because it
changes the development posture: the iGPU drives the physical panel of a family
laptop in production use. A GPU hang or TDR triggered by a malformed command
stream is not a background failure — it is a visible fault for a non-technical
user, and recovery may need the VM restarted.
*Mitigation:* do development against a software Vulkan implementation
(lavapipe) on the GPU side wherever possible, which is also the fastest way to
iterate. `zink-venus-lavapipe` in Mesa CI proves the whole stack works over a
forwarded, CPU-backed Vulkan.

## 9. `unsafe`, and what can be tested under Miri

R7 is the one place the security stance stays strict, and it is worth being
concrete about what "safe by construction" can actually mean here.

**Confine `unsafe` to three modules**, each with written invariants:

1. **The mapping.** One place that turns a file descriptor or device handle into
   a `&[UnsafeCell<u8>]`-shaped region, with the invariant "these bytes may be
   mutated by another process at any time".
2. **The ring.** Head/tail/status accessed only through `AtomicU32` with
   explicit orderings; the buffer accessed only through raw reads and writes of
   byte slices.
3. **The arena allocator.** Offset arithmetic and sub-slicing.

Everything else — the generated marshalling, the handle table, the protocol
logic — should be safe Rust operating on `&[u8]`/`&mut [u8]`.

**Making generated marshalling safe by construction is largely achievable**, and
is the single biggest correctness lever available:

- **Never transmute a struct out of shared memory.** The temptation is to cast
  a `&[u8]` to `&VkFoo` because the layouts match. Do not: the peer can mutate
  it, so a `&VkFoo` would be an immediate aliasing-model violation, and padding
  bytes make it unsound regardless. Generate **field-by-field reads** from a
  cursor over `&[u8]`. This is what both Venus and gfxstream do in C, and it is
  the same shape in safe Rust.
- **Generate a bounds-checked cursor**, not pointer arithmetic. A
  `Cursor<'a> { buf: &'a [u8], pos: usize }` with `read_u32() -> Result<u32>`
  makes every decode fallible and every overrun a returned error rather than
  undefined behaviour. The cost is a comparison per field, which is noise next
  to the work being done.
- **Encode the count/array relationship in the generated types.** Where
  `vk-parse` gives `len="bindingCount"`, generate code that reads the count
  first and then loops — never a slice constructed from a peer-supplied length.
- The only genuinely unavoidable `unsafe` in the generated layer is at the ICD
  boundary itself: `extern "system"` entry points taking raw pointers from the
  application. Keep those functions to a mechanical
  "null-check, dereference, call a safe inner function" shape so that the unsafe
  block is one line and identical in every generated stub.

**What Miri can and cannot do here.** Miri will not run the real thing — no
loader, no shared mapping, no peer process. But it can test a great deal if the
code is structured for it:

- **The arena allocator, fully.** Back it with a plain `Vec<u8>` in tests and
  Miri validates all the offset arithmetic, alignment and free-list logic. This
  is high value because allocator bugs are exactly the silent-corruption class.
- **The ring, single-process.** Run producer and consumer as two threads over a
  `Vec<u8>`; Miri's stacked-borrows and data-race detection will catch aliasing
  errors and missing atomics. `-Zmiri-many-seeds` and preemption make the
  interleaving search genuinely useful for a lock-free structure.
- **Generated marshalling round-trips.** Encode a value, decode it, compare —
  under Miri, on a `Vec<u8>`. This catches the R8 class (wrong `len=` handling)
  and any provenance mistake in the cursor.
- **What it cannot check:** the cross-process race is outside Miri's model by
  construction, as `security-model.md` observes about the language generally.
  A peer mutating the buffer concurrently is, strictly, a data race that no
  amount of Rust reasoning makes sound. The honest framing is that we model the
  shared region as raw bytes with no Rust-level aliasing claims, keep all access
  through atomics or byte-wise copies, and accept that this is a place where the
  language's guarantees stop.

**Differential testing beats reasoning here.** Generate the encoder and decoder
from the same model, then property-test round-trips over randomly generated
structures including pNext chains — and, crucially, test *against a second
implementation* where one exists. Venus's generated C headers are MIT and can be
compiled into a test harness; agreeing byte-for-byte with them on the shared
subset would be very strong evidence the generator is right, and far more
convincing than symmetric self-consistency (which R8 correctly identifies as
proving nothing).

## 10. What I could not confirm

Listed plainly, because the requirement was evidence rather than confidence.

1. **Whether *this machine's* Intel Windows driver exposes
   `VK_EXT_external_memory_host` at runtime, its `minImportedHostPointerAlignment`,
   and whether `vkGetMemoryHostPointerPropertiesEXT` returns non-zero for a
   pointer into the candidate arena.** gpuinfo evidence puts support at "yes,
   4096" for RPL-P siblings (§2.1), but that is inference from sibling PCI IDs,
   not this device. **I connected to the host to run `vulkaninfo` directly and
   could not**: the Windows guest's SSH refuses my forwarded keys, the QGA and
   QMP sockets under `/run/windows-vm/` are root-owned and I do not have root on
   the host, and the only guest-execution channel is the virtiofs share, into
   which dropping an executable would mean running code in a family member's
   production Windows session — which the hard constraints forbid. So this
   remains unmeasured. It is still the single most important unknown, and the
   gate on everything; it needs either guest credentials or host root, whichever
   is easier to arrange. What the connection *did* establish is in the note
   below.
2. **Whether `vkGetMemoryHostPointerPropertiesEXT` accepts a pointer into a PCI
   BAR mapping** (the ivshmem case) rather than ordinary RAM. The KVM analysis
   in §2.2 shows such pages are not `is_mmio` from the hypervisor's point of
   view, which is encouraging, but the driver may still refuse. Not confirmed.
3. **Whether Windows AWE's `AllocateUserPhysicalPages` returns real
   guest-physical frame numbers.** Under investigation. If it does, the arena
   needs no device and no driver at all, which would be the best outcome
   available.
4. **Whether the Windows `viofs` driver implements the virtio-fs DAX window.**
   I believe it does not — it is a WinFsp user-mode filesystem whose
   memory-mapped files are backed by the Windows page cache — but the `viofs`
   README fetch returned an empty file and I found no explicit statement either
   way.
5. **Whether `VK_EXTERNAL_MEMORY_HANDLE_TYPE_OPAQUE_WIN32_BIT` can import an
   arbitrary section object from `CreateFileMapping`,** or only handles produced
   by `vkGetMemoryWin32HandleKHR`. I believe the latter, which would make it
   useless for importing a foreign shared region, but this is decisive and I did
   not confirm it.
6. **The VAR thesis.** Its problem statement matches ours more closely than any
   other prior art, and I could not retrieve the full text — the PDF endpoint
   returns 403 to WebFetch and resets the connection to `curl` from this host.
   Worth fetching manually for its memory-mapping and presentation chapters.
7. **Whether WINQ-EMU's Windows virglrenderer patches are upstreamed or
   complete.** Their README claims they are minimal and upstreamable; I did not
   read the diff. This matters only as evidence that a Venus-style GPU-side
   renderer runs on Windows, which it does establish either way.
8. **Whether the `kumquat` server builds and runs on Windows.** crosvm ships on
   Windows and `rutabaga_gfx` builds there, but I could not verify kumquat
   specifically. Relevant if we choose to reuse rather than reimplement.
9. **The resolution of virtio-win issue #217** ("Signed build of IVSHMEM").
   GitHub rate-limited me before I could read the thread. It is largely moot —
   the Looking Glass installer's driver was independently verified as
   Microsoft-signed — but the upstream position would be useful context.
10. **Zink's presence on the Khronos OpenGL *ES* conformant-products list.**
    Confirmed for desktop GL 4.6; the ES list returned no zink match, which may
    be a search failure rather than an absence.
11. **Whether virglrenderer's `vkr` renderer could be built for Windows and
    reused wholesale** as our GPU-side server. WINQ-EMU suggests yes; nobody has
    done it in our direction, and I did not assess the effort.

## 10a. What connecting to the live machine confirmed

I logged into `testhost` (as the unprivileged user; no host root, no guest
login) and read the running QEMU command line. This replaces several assumptions
with ground truth:

- **Machine type is `pc` (i440fx), not q35**, with `smm=off`. This corrected the
  GPA→memfd formula in §2.2 (i440fx computes the below-4G split differently) and
  removed the spurious TSEG concern (no SMM means no TSEG at all).
- **The entire 13 GiB of guest RAM is a single
  `memory-backend-memfd,id=virtiofsmem,size=13312M,share=on`**, attached as the
  sole NUMA node. So "the arena lives in guest RAM that the host can already
  mmap" is not a hoped-for property — it is the literal current configuration,
  forced by virtio-fs and shared with nothing else.
- **No ivshmem device is currently attached.** Adding one is a config change to
  `windows-vm.service`, not something already present. Given §2.2's conclusion
  that a BAR arena is the least-good option anyway, this is fine.
- **`virtio-win 0.1.285` is the mounted guest-tools ISO**, which is ≥ 285, so the
  signed `viosock` (vsock) driver is available to install per §6.3 — confirming
  that transport option concretely rather than by version-table inference.
- Three `vfio-pci` passthroughs: the iGPU (`0000:00:02.0`, with an IGD option
  ROM and `x-igd-opregion=on`), plus `00:14.0` and `00:0d.0` (USB/TB
  controllers). `virtio-balloon` is present — normally a hazard for a fixed
  arena, but under VFIO the pages are pinned, and AWE pages are locked besides.
- QEMU binary is a pinned `qemu-host-cpu-only-battery-10.2.2` build, matching
  `hardware-constraints.md`.

None of this measured the one thing that gates the design — whether the GPU-side
driver imports arena pages — because that needs code running inside Windows,
which I could not reach. But it does confirm the transport and memory
substrate the design assumes, and it means step 1 of §7.3 is now purely "get a
`vulkaninfo` to run in the guest", with the host side already understood.

## 11. The three biggest technical risks

Reduced to three, in order.

### 1. The arena may not be importable as `VkDeviceMemory`

Everything rests on the GPU-side driver accepting arena pages via
`VK_EXT_external_memory_host`. If `vkGetMemoryHostPointerPropertiesEXT` returns
`memoryTypeBits == 0` — a legal driver response — then there is no zero-copy
path, and the project either falls back to the copying mode of §2.6 (which does
not meet the stated requirement, and which `bufferDeviceAddress`-using clients
defeat anyway) or does not proceed in this form. This is R9, and it subsumes the
"which pages" question of §2.2, because the two candidate arena locations differ
mainly in how likely the driver is to accept them.

It is also, mercifully, the cheapest risk to retire: a `vulkaninfo` run and a
ten-line probe program, an afternoon's work. **Do it before anything else.**
Nothing else in this document should be built on until this is answered.

### 2. The API surface is large enough to fail on volume alone

The measured precedents are ~70,000 generated lines for Venus's curated ~52% of
the API and ~117,000 per side for gfxstream's full coverage, on top of ~30,000
lines of hand-written semantic glue that codegen cannot produce — the
`deviceMemoryTransform` offset rewriting, the delayed-destroy machinery, the
resource tracker. And the pieces vk.xml genuinely cannot express are not
marginal: unions with no discriminator (only 10 `selector=` annotations exist),
the 103 opaque `void*` members, `optional=` semantics that gfxstream's own
source warns are unstable across header releases, and the "little Lisp"
gfxstream had to invent to decide whether `pTessellationState` is present.

The mitigations are real but must be chosen deliberately: scope to Zink's
requirement set first rather than the whole registry; build the type model once
and properly rather than re-deriving it per pass; and treat the generator as the
first real component of the project, which `api-scale.md` already concludes.
The failure mode here is not a wrong decision, it is running out of momentum
against a large mechanical surface — so the milestone at §7.3 step 3, a working
end-to-end round trip over a deliberately tiny command set, matters more than
its size suggests.

### 3. Silent corruption, from three directions at once

This project has an unusually high ratio of ways-to-be-subtly-wrong to
ways-to-crash, and they compound:

- **Version skew** (R13). The wire format encodes command length implicitly, so
  two builds from different registry or generator versions do not fail to
  connect — they desynchronise and misinterpret everything downstream.
- **Cache attribute mismatch** (R10). Mapping the same physical pages with
  different attributes on the two sides is undefined on x86 and shows up as
  corrupted texture data under load rather than a fault.
- **Generator bugs** (R8). A wrong `len=` interpretation produces marshalling
  that is wrong *identically on both sides*, so it round-trips cleanly and looks
  correct while writing past the end of a buffer.

None of these produces a stack trace. All three are addressable, but only by
deciding to address them early: an explicit wire-format version and protocol
hash exchanged in the handshake; cache attributes negotiated per sub-region and
never chosen independently; and differential testing of the generated
marshalling against Venus's MIT-licensed generated C on the shared subset,
rather than trusting the symmetry of our own encoder and decoder. Add to that
the development posture in R18 — iterate against lavapipe on the GPU side, not
against the iGPU that drives someone's laptop panel.
